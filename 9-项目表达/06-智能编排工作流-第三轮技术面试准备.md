## 0. 第三轮在考什么

| 前两轮 | 第三轮 |
|---|---|
| 是什么、怎么做 | **为什么这么做、代价是什么** |
| 你会不会用 | **你能不能判断** |
| 功能是否完整 | **边界是否清楚** |
| 你做成了什么 | **你个人做了什么** |
| 有没有数据 | **数据可不可信、口径是什么** |

**一句话**：三面考的是"**你有没有能力为一个技术决策负责**"。

所以准备的重心不是"多讲功能"，而是：

1. 一条清晰的叙事线
2. 三层以上的技术纵深
3. 主动交代局限
4. 数字和口径对得上
5. 分清个人贡献与团队资产

## 1. 项目陈述：四个时长版本

### 1.1 三十秒（电梯版）

> 我做的是团队的一套 AI 研发工作流。核心不是"让团队用上 AI 工具"，而是**把研发流程编码成 AI 必须执行的行为约束**——七个阶段做成显式命令，文档不落盘不能进下一阶段，关键节点用 hook 做门禁，缺设计文档时 AI 想写代码会被直接拦停。同时每个阶段自动采集耗时、介入轮次和返工原因，形成一个可度量的闭环。

### 1.2 两分钟（标准版）

> 我做的是国际化外卖前端团队的一套 AI 研发工作流。
>
> 背景是：团队都在用 AI 写代码，但用法完全是个人化的——有人让它一次写几百行，有人只用它补全。结果就是质量不稳定、责任说不清、经验沉淀不下来。
>
> 我的判断是：**问题不在于模型不够强，而在于没有工程约束**。所以我做的是把研发流程本身编码成 AI 的行为规则。
>
> 具体三块：
> 第一，**流程可执行**。把需求分析、设计、计划、测试、编码、CR、归档七个阶段做成 13 个显式命令，每个阶段有固定剧本，文档不落盘不能进下一阶段。
> 第二，**过程可控**。在 Claude Code 的 hook 层加门禁，分硬阻断、软警告、静默三档：缺设计或计划文档时写代码会被 `exit 2` 拦停，提交前必须过 CR 和安全扫描；风格类问题只提示，避免把团队卡死。
> 第三，**效果可证**。每个阶段自动采集耗时、介入轮次、返工归因和 token 成本，写进一份 eval-log，再渲染成报告推到团队大盘。
>
> 目前大盘上覆盖 **30 个项目、累计 89 条需求**。我的角色是这套东西的建设和推进者：流程抽象、门禁分级、评测口径是我定的；底层依赖的 AST 知识图谱和技能分发工具是团队已有能力，我做的是把它们编排进流程。

### 1.3 五分钟（深挖版）

在两分钟版基础上，按这个顺序展开：

1. **问题定义**（40 秒）：不是"AI 不会写"，是"AI 写的东西不可控、不可度量、不可复用"
2. **架构选择**（60 秒）：为什么用命令驱动而不是让 AI 自主规划——可控、可审计、责任边界
3. **门禁设计**（60 秒）：硬阻断 / 软警告 / 静默的三级依据；为什么挂在 `UserPromptSubmit` 而不是写文件时
4. **上下文工程**（50 秒）：分层加载（常驻薄路由器 / 按需图谱 / 源码用完即丢）
5. **度量闭环**（50 秒）：一个需求一份 eval-log；自动采集 vs 人工填报的分界
6. **一个具体例子**（40 秒）：故意不跑 plan 直接说"开始编码"→ 被拦停并提示缺什么

### 1.4 十分钟（架构级）

五分钟版 + 以下两块：

- **取舍与代价**：AST vs 向量检索、物理门禁 vs 提示词、统一升级 vs 项目个性化
- **局限与演进**：哪些地方会失效、如果重做会改什么

## 2. 叙事主线：一条线 + 三个支点

```
主线：把研发流程编码成 AI 的行为约束

支点 1  流程可执行  → 命令 + 文档先行
支点 2  过程可控    → 门禁分级 + 确认隔离
支点 3  效果可证    → 评测闭环 + 真实大盘
```

**为什么要一条线**：三面会反复把你拉回"这到底解决了什么问题"。有主线就不会散成功能罗列。

**备用的一句话**：

> 不是让 AI 更聪明，而是给它一个工程师的工作环境。

## 3. 技术纵深地图（面试官会往下钻的 5 层）

| 层级 | 会被问什么 | 你的答法核心 |
|---|---|---|
| **L1 机制** | 命令、hook、文档怎么协作 | 命令触发剧本 → hook 在剧本外拦截 → 文档当状态机 |
| **L2 设计** | 为什么这么拆 | 每层解决一个失效模式：不可控 / 不可审计 / 不可度量 |
| **L3 边界** | 哪里会失效 | 命中关键词才拦、绕过工具链就失效、软警告可一路确认 |
| **L4 演进** | 如果重做改什么 | 见 §7 |
| **L5 组织** | 怎么推动、怎么度量 ROI | 见 §6、§8 |

**能答到 L3 是三面的分水岭**——只讲功能的人停在 L2。

## 4. 八个高概率深挖问题

### Q1：这和"直接用 Cursor / Claude Code"有什么本质区别？

> 区别不在工具，在**约束在哪一层**。
>
> 直接用 AI，约束在提示词和人的自觉上——你让它别跳过设计，它可能跳过；你忘了检查，就没人检查。
>
> 我这套是把约束下沉到**协议层**：缺 Design/Plan 时，hook 直接 `exit 2` 拦截工具调用，模型连开始写的机会都没有；提交前 CR 状态不对，`git commit` 会被拦。**提示词是请求，`exit 2` 是不允许。**
>
> 另外多了一层"可度量"——直接用的效果只能靠体感，这套每一个阶段都有客观数据落盘。

### Q2：门禁为什么用 hook 而不是提示词？有没有失效场景？

> 有两个原因：一是强度，二是时机。
>
> 强度上，`exit 2` 是宿主层拦截，不依赖模型配合。时机上，"文档先行"挂在 `UserPromptSubmit`——它在模型开始处理**之前**就跑完了。如果挂在写文件时，模型已经决定要写了，那只是事后纠正。
>
> **失效场景有三个，我主动说**：
> 第一，意图识别靠关键词。用户不说"impl"而直接说"帮我改这个文件"，门禁不触发。这是必要妥协——否则日常问答全被拦。
> 第二，完全绕过工具链就不受约束。不在 Claude Code 里写、或者直接改文件不提交，门禁都不生效。
> 第三，软警告可以一路"继续"通过。
>
> 所以准确的表述是：**它保证"走标准路径时流程不会被无意跳过"，不是"任何人任何时候都绕不过去"**。

### Q3：知识图谱为什么用 AST 不用向量检索？规模上限在哪？

> 因为我要的是**确定性和可定位性**。AST 提取的是结构事实——谁调用了谁、改这个文件波及哪些模块——每条结论能落到 `file:line`，而且提取过程不消耗 token。
>
> 向量检索适合"语义模糊匹配"，但工程影响面分析需要的是精确的调用链，召回的相似代码反而会引入噪声。
>
> 规模上限也明确：全量扫描到几百个文件没问题，但全项目重建成本高，所以我做了增量模式——按基线 commit 做 diff，只刷受影响节点和 1-2 跳反向依赖，几秒完成。再往上，就需要把图存到外部服务，而不是每次落 JSON。

### Q4：评测数据可信吗？AI 自己总结的介入轮次怎么保证？

> 分两类看。
>
> **客观数据是完全可信的**：阶段耗时是命令前后取系统时间，token 是扫会话日志按时间窗口归属，文件数是实际写盘统计。这些不经过 AI 判断。
>
> **介入轮次确实是 AI 自述的**——这是这套度量的真实局限。我们做的是两条：一是红线规定只能记本次真实发生的，缺失就留空，禁止事后推断补全；二是有测试用例守着这条红线。
>
> 但要诚实说：**它能防"事后编造"，防不住"当场记错"**。所以我把这套定位成**过程透明型度量**，不是客观审计型。真要审计，得在宿主层做结构化埋点，成本高得多。

### Q5：30 个项目是真用还是"装了"？怎么定义活跃？

> 这个口径我必须说准。
>
> 大盘上现在有 **30 个项目、89 条需求**，最近一条是今天更新的，有需求完整跑完了六个阶段——这说明**是真的在跑，不是装了就放着**。
>
> 但"89 条"是**累计需求数**，不等于"30 个项目都活跃"。有些项目只有一两条，属于试点验证。所以我的表述是"覆盖 30 个项目、累计 89 条需求"，不说"30 个项目每天都在用"。

> ⚠️ 如果被追问"多少人在日常使用"，这个数你需要提前确认——见 §9 待补清单。

### Q6：这套东西最大的成本是什么？ROI 怎么算？

> 成本有三块：
> **第一是流程本身的摩擦**——每个阶段要确认，一个需求下来十几二十次交互。这是有意的，用人力换可控性。
> **第二是维护成本**——技能要跟着模型和工具演进，门禁要跟着团队规范调整。
> **第三是 token 成本**——虽然有分层加载和缓存优化，但长需求仍然有开销。
>
> ROI 我不报大盘百分比，因为归因不干净——需求难度、人员变动都会干扰。我只讲两类可追溯的账：单个需求的人工预估耗时 vs 人机对话时长，以及 CR/返工的实际变化。**宁可讲小账讲得清，不报大数讲不清**。

### Q7：如果让你砍掉一半功能，你会砍什么？

> 我会保留三样：**文档先行、编码前置门禁、评测落盘**。这三样构成最小闭环——流程有约束、约束可拦截、结果可度量。
>
> 可以砍的：知识图谱（能降级为 grep）、多样化的 CR 模式（先只留默认）、经验沉淀和多语言支持。这些是效率增强，不是闭环必需。
>
> 判断标准很简单：**砍掉之后，"AI 会不会跳过流程"和"我们知不知道效果"这两个问题还答不答得上来。** 答得上就砍。

### Q8：落地过程中出过什么问题？怎么处理的？

> 主要不是技术问题，是**接受度问题**。
>
> 一开始的阻力是"流程太重、还要写文档"。我的处理是分两步：先用一个真实需求跑通，把"被门禁拦下"的场景演示给团队看——大家发现拦的是真问题，不是形式主义；然后把门禁分级，风格类只提示不阻断，紧急修复留了跳过通道。
>
> 技术上也踩过坑：比如门禁意图识别误判、模板和实际项目不匹配。这些最后都归到一条原则——**门禁太严等于没有门禁**，必须给例外留通道。

### 5.1 可以直接说（已验证）

| 数字 | 口径 | 备注 |
|---|---|---|
| **30 个项目 / 89 条需求** | 团队大盘累计 | 截至 2026-10-14，最近更新当天 |
| **7 个主阶段 + 1 个评测** | 流程设计 | ard/design/plan/test/impl/cr/archive/eval |
| **13 个 `/soda:*` 命令** | 命令数 | 含 soda-init |
| **8 种项目类型** | 类型注册表 | 前端 H5/中后台 + 5 种后端 + 全栈 |
| **3 类 hook 挂点** | 门禁设计 | UserPromptSubmit / PreToolUse / PostToolUse |
| **两级门禁强度 + 静默** | 门禁分级 | 硬阻断 / 软警告 / 无输出 |
| **6 个阶段的数据采集** | eval-log | ard/design/plan/impl/cr/test |

### 5.2 要交代口径才能说

| 数字/说法 | 必须补的口径 |
|---|---|
| 提效倍数 | `manual_dev_hours / ai_dev_hours`，且 ai 是**对话墙钟时间**，不是等效工时 |
| 一次通过率 | 是**文件级**，改一行也算整个文件返工 |
| PRD 完备度 | "不涉及"计入分子 |
| 89 条需求 | 累计，不等于活跃项目数 |

### 5.3 绝对不能说

- ❌ "部门整体交付周期下降 X%"——归因不干净
- ❌ "AI 替代了多少人力"
- ❌ "我们有完整的 CI/CD"——实际是手工审查，**这条主动讲反而是加分**
- ❌ 把团队已有的 code-map / d-skills 说成自己写的
- ❌ 任何没确认过的覆盖人数

## 6. 个人贡献边界（这一节必须自己核实）

三面一定会拆"你做的"和"团队做的"。建议按这个框架准备，**每一条都要能举出一个具体动作**：

| 类别 | 需要你确认/补充的内容 | 建议表述 |
|---|---|---|
| **我主导** | 流程抽象、命令剧本、门禁分级、评测口径、推广 | "这套流程的抽象和门禁设计是我定的" |
| **我参与** | 知识图谱的消费侧、模板设计、具体项目落地 | "图谱能力是团队已有，我负责把它编排进流程" |
| **我依赖** | 技能分发工具、AST 图谱、外部技能（brainstorming / code-reviewer 等） | 主动说明，别被问出来 |
| **团队协作** | 大盘运维、其他项目的落地推动 | 分清"我推的"和"别人接的" |

> 原则：**主动划边界。** 被面试官发现你在模糊归属，比承认"这部分是团队做的"损失大得多。

## 7. 如果重做，会改什么（演进题准备）

这道题几乎必问，提前准备三个具体的、有技术含量的答案：

1. **把"确认"从模型自觉变成硬停点**
   现在只有需求分析阶段有显式的大纲确认，设计/计划/测试是润色后直接落盘。如果重做，会把大纲确认做成统一的宿主层能力，而不是靠命令文件自觉。

2. **把度量从"AI 自述"改成"宿主埋点"**
   介入轮次现在是 AI 结束后总结的。更可靠的做法是在宿主层记录用户与模型的每一次实质交互，从根本上消除"自述"的不确定性。

3. **把门禁从"关键词触发"改成"意图分类"**
   现在是正则匹配关键词，会漏也会误判。可以用小模型做意图判断，代价是每次消息多一次推理开销——这是个明确的成本/准确率取舍。

> 这三个答案的共同点：**都指向"现在的实现是权衡后的产物，我知道它哪里不够"**。

## 8. 反问环节（三面必答好）

挑 2 个问，别问薪资和加班：

1. **"团队现在怎么度量 AI 编码的效果？是看采纳率，还是看交付周期？"**
   —— 展示你对度量的关注，也能探到团队成熟度。

2. **"这个岗位对 AI 工程化的期待，是工具建设，还是推动研发流程变革？"**
   —— 展示你理解这两件事不是一回事。

3. **"团队怎么看待 AI 生成代码的验收标准和责任边界？"**
   —— 展示你关心质量和责任，而不只是效率。

## 9. 面试前 1 小时速览清单

### 必须确认的数字（目前还缺）

- [ ] 部门级覆盖的**人数**
- [ ] 一个真实需求的 `ai_dev_hours` 与 `manual_dev_hours`
- [ ] 日常**真实使用者人数**（不是"装了"）
- [ ] 你个人主导 vs 参与的具体边界（§6）

### 开场前默念

- [ ] 一句话主线：**把研发流程编码成 AI 的行为约束**
- [ ] 三个支点：流程可执行 / 过程可控 / 效果可证
- [ ] 三个局限：关键词触发 / 绕过即失效 / 软警告可一路确认
- [ ] 一句定性：**保证"不被无意跳过"，不是"绕不过去"**
- [ ] 一个案例：不跑 plan 直接说"开始编码"→ 被 `exit 2` 拦停

### 临场避坑

- 不抢话，被追问细节时先说"我分三层说"
- 数字先给口径再给值
- 不会的说"这块是团队做的，我了解的是……"
- 被质疑时先承认合理部分，再给边界
