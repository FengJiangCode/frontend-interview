# 模块一 · 设计原则

## 1.1 一句话

**把研发流程本身编码成 AI 的行为约束，而不是让 AI 更聪明。**

> 原话："不是让 AI 更聪明，而是给它一个工程师的工作环境。"

## 1.2 三条核心理念

| 理念 | 具体表现 | 为什么 |
|---|---|---|
| **命令模式唯一触发** | 13 个 `/soda:*` 命令，无自动模式；非命令消息一律不加载 Skill | 可控、可审计、责任边界清晰 |
| **文档先行不可绕过** | 文档不落盘不能进下一阶段，文档没确认不能写代码 | 用物理门禁对抗 AI "跳步"的天性 |
| **AI 提速补全，人定边界** | 每个关键节点 `HARD STOP` 等确认；"确认隔离原则"不许批量跳过 | 出了问题能追溯到是哪次确认放行的 |

## 1.3 三层结构（讲架构时的抓手）

把它想成一条**必须签字的流水线**：

| 角色 | 对应 | 作用 |
|---|---|---|
| **工位** | `commands/soda/*.md`（13 个命令剧本） | 每道工序做什么 |
| **监工** | `hooks/` + `RULE.md` | 不合格不放行（`exit 2`） |
| **图纸** | `docs/knowledge/` | AI 靠它知道项目长什么样 |

## 1.4 门禁的三级力度（最能体现判断力的一点）

| 力度 | 触发条件 | 例子 |
|---|---|---|
| **硬阻断**（`exit 2`） | 安全红线、流程完整性 | 缺 Design/Plan 就写代码、`eval()`、内网 IP、私钥 |
| **软警告**（`exit 0`） | 风格、状态类问题 | `console.log`、工作区脏、在 main 分支 |
| **静默通过** | 无问题 | 脚本完全不输出，注释写明"保持上下文干净" |

**关键判断**：分级比"全拦"或"全不拦"都难做。漏拦会出事，误拦会被团队绕过——**门禁太严等于没有门禁**。

## 1.5 七条关键取舍（面试可直接背）

| 取舍 | 选择 | 理由 |
|---|---|---|
| 命令驱动 vs 自动模式 | 命令驱动 | 可控、可审计、责任边界清晰 |
| 提示词约束 vs 物理门禁 | 物理门禁 | 提示词会被忽略，`exit 2` 不会 |
| 全拦 vs 分级 | 分级 | 安全硬拦，风格提示，判断权留给人 |
| AST 知识图谱 vs 向量检索 | AST | 结构事实确定、可定位到 `file:line`、零 token 提取 |
| 常驻上下文 vs 按需加载 | 分层按需 | 常驻只留薄路由器，避免每次对话固定吃上下文 |
| 统一升级 vs 项目个性化 | 两层配置分离 | 前者保统一，后者保落地 |
| 全自动采集 vs 人工填报 | 能自动则自动 | 时间戳/文件数/token 自动；主观工时人工 |

# 模块二 · 环境搭建

## 2.1 一句话

**把 `.agents/skills/` 下的一个静态分发包，激活成一个可运行的项目环境。**

激活产物 = **5 个部件 + 2 个配置点 + 3 个 git hooks**。

## 2.2 十步动作与产物

| # | 动作 | 产物 |
|---|---|---|
| 0 | 检测项目类型 | `workflow.config.yaml: project.type` |
| 1 | 建 docs 结构 | `docs/{features,knowledge,rules,review}` |
| 2 | 生成 AI 规则 | `.claude/rules/rule.md`、`CLAUDE.md`、`docs/rules/*` |
| 3 | 初始化门禁 | `.claude/settings.json` |
| 4 | 生成项目配置 | `workflow.config.yaml` |
| 5 | 更新 `.gitignore` | 技能层忽略条目 |
| 6 | 生成 docs 说明 | `docs/README.md` |
| 7 | 拉依赖 Skills | `.agents/skills/modules/` |
| 8 | 拉模板 | `templates/` |
| 9 | 装 git hooks | `post-checkout` / `post-merge` / `post-rewrite` |
| 10 | 下发命令 + 注入 header | `.claude/commands/soda/*.md` |

## 2.3 最关键的分叉：`project.type` 是总开关

技能、模板、命令行为**三者全部从它派生**。改一个字段，下游全变：

| | `frontend-h5` | `frontend-gattaran`（中后台 Vue） |
|---|---|---|
| 依赖技能数 | 13 | **15**（多 `field-config-designer`、`mid-backend-standards`） |
| 文档模板 | Fe 系列 3 个 | **Gattaran 系列 3 个** |
| `design` 加载技能 | 无 | `field-config-designer` |
| `impl` 加载技能 | `vue-standards-detector` | `mid-backend-standards` |

## 2.4 三处值得单独讲的设计

**① `CLAUDE.md` 只写一行**

```
@.claude/rules/rule.md
```

规则本体被逐字节复制到 `.claude/rules/rule.md`，入口只留一个 `@` 引用。**这是"常驻成本控制"的落点**——改规则只改一处，入口不动。

**② 门禁是"双层 × 三挂点"**

```
UserPromptSubmit             → before_impl_check.sh    （无 matcher，匹配人类输入）
PreToolUse(Bash git commit*) → before_commit_check.sh  + haiku 语义门禁
PostToolUse(Write|Edit)      → after_code_scan.sh      + haiku 查 ARD/Design 质量
```

每个挂点都是**机械层（shell）+ 语义层（haiku 小模型）**配对：能写成正则的走 shell（快、零 token），判断不了语义的交给小模型读 markdown 规则。

另外两个细节：`"disableAllHooks": true` 是白名单式配置（先关自动发现，再逐条声明）；这一步**刻意排在拉取依赖之前**，断网也能先装上门禁。

**③ 命令下发时会"注入 header"**

`commands/soda/*.md` 不是原样拷贝，而是**按配置为每个命令生成一段"Skill 加载顺序"表头**。意义：命令文件不硬编码依赖，依赖关系收敛到 config 一处。

## 2.5 两层配置 = "规模化"三个字的答案

| 层级 | 内容 | 重跑 init 时 |
|---|---|---|
| **技能层** | `.agents/skills/`、`.claude/commands/`、`.claude/rules/` | **每次全量覆盖** → 保证统一升级 |
| **项目层** | `workflow.config.yaml`、`docs/rules/`、`docs/knowledge/` | **永不覆盖** → 保证项目个性化 |

**下发新版 = 各项目重跑一次 init，项目自己的配置和知识图谱不受影响。** 统一升级与项目个性化不冲突。

## 2.6 幂等性与一个例外

项目层产物已存在则跳过；技能层每次覆盖。

**例外**：`.claude/settings.json` 已存在时也跳过，想刷新门禁配置必须显式加 `--force`。

# 模块三 · 工作流运行

## 3.1 一句话

**一个需求 = 一条必须签字的流水线；`docs/features/active/{需求名}/` 是它的状态机。**

## 3.2 完整生命周期

```
/soda:ard → /soda:design → /soda:plan → /soda:test → /soda:impl
                                                          ↓
                        /soda:archive ← /soda:cr ←────────┘
                             ↓
                  自动触发 /soda:map --update（刷新知识图谱）
                             ↓
                   /soda:eval（出评测报告 → 传 S3 → 刷大盘）
```

旁路命令：`map`（建图）`sync`（变更同步）`fix`（排障）`mock`（接口）`exp`（经验）

**关键**：各阶段产物都落在同一个需求目录里，下一阶段读上一阶段的产物。**文档不是副产物，是传送带。**

## 3.3 每个阶段的固定骨架

| Step | 做什么 | 硬约束 |
|---|---|---|
| **-1** | 确认类型 + 收输入 | `ard` 没有 PRD 就 **HARD BLOCK** |
| **0** | 装上下文（知识图谱探针） | 图缺失时 **HARD STOP**，可回"跳过"降级 grep |
| **1** | 按配置顺序跑 input Skill | **每个 Skill 单独确认**，不得批量跳过 |
| **2** | 读模板 | 优先级：`config.output` > `project.type` 默认 > 嗅探 |
| **3** | 中文润色（Humanizer，去机器腔） | 固定动作 |
| **3.5** | 🛑 输出大纲等确认 | **确认前禁止写任何文件** |
| **4-5** | 落盘 + 更新 progress.md | 文件名、路径、章节结构固定 |
| **末步** | 写 eval-log | 标注"必须执行，不得跳过" |

**编码实施（`impl`）是唯一按任务粒度循环的阶段**：

```
标记 [🔄] → 规范合规预检 → Read 目标文件 → 精准实施 → 标记 [x] → 输出进度
```

预检对照三张表：`FORBIDDEN_LIST`（命中即 HARD BLOCK）、`TECH_ALLOWED`（引入未列依赖要停下确认）、`CODE_STYLE`。**规范优先级：`docs/rules/` > Design 规格 > Plan 描述 > 任何 Skill 建议。**

## 3.4 运行时真正拦人的地方

控制流不在剧本里，在 hooks。三个挂点、三种力度：

| 挂点 | 时机 | 检查 |
|---|---|---|
| `UserPromptSubmit` | 每条消息发出前，**模型还没开始处理** | 意图识别命中 impl → 查文档就绪 |
| `PostToolUse`(Write\|Edit) | 每次写文件后 | `eval()` / `v-html` / 硬编码密钥 硬阻断 |
| `PreToolUse`(git commit) | 提交前 | CR fail / 敏感信息 / 内网 IP / 私钥 硬阻断 |

**为什么"文档先行"挂在 `UserPromptSubmit`**：它在模型开始思考之前就跑完了。挂在写文件前是事后纠正（那时模型已经决定要写了）；挂在消息入口，是"要发车"这个念头出现的当下就拦，还能把"你缺哪份文档"提前喂回去。

**`asyncRewake` 的设计**：代码扫描挂在 `PostToolUse` + `asyncRewake` 上——后台跑不阻塞，**只在 `exit 2` 时把模型叫醒**。平时零成本、出事才介入。

## 3.5 知识闭环

| 动作 | 命令 | 产物 |
|---|---|---|
| 建图 | `/soda:map` | AST 管道零 token 提取：`nav-parser` → `graph-cluster`(聚类) → `deep-analyzer` |
| 用图 | ard / design / fix / cr | 优先读路由索引进具体节点，**找不到才降级 grep** |
| 保鲜 | archive / sync 自动触发 | 按 `base_commit` 做 diff，只刷受影响节点及 1-2 跳 |

**配套的分层上下文加载**：Tier 1 常驻（规则 + 薄路由器，经 `CLAUDE.md` 的 `@` 引入）→ Tier 2 命中意图后按需读 → Tier 3 源码用完即丢。

## 3.6 数据与评测闭环

**一个需求一个 `eval-log.yaml`**，七块数据：

| 块 | 内容 |
|---|---|
| `meta` | 需求号 / 项目 / 分支 / owner |
| `context_checklist` | PRD 完备度 8 项，四态（就绪/缺失/不涉及/未确认） |
| `stages` | 六阶段：时间戳、Skills、介入轮次、未决待办 |
| `rework_log` | 返工归因五分类 + 影响量级 |
| `archive_assessment` | AI 耗时(自动) / 人工估值 / 代码占比 |
| `token_by_stage` + `token_summary` | 四类 token 分阶段 + 汇总 + 成本 |

**采集三来源**：

| 类别 | 谁产生 | 自动化 |
|---|---|---|
| 时间戳 | 命令跑 `date` | 全自动 |
| Token | 扫会话 JSONL，按阶段时间窗口归属 | 全自动 |
| 介入轮次 | **AI 结束时不问用户、自己回顾总结** | 半自动 |
| 主观评估 | 人填 | 人工 |

**上传**：渲染成单文件 HTML → `{项目}/{分支}.html`；同时 merge 进 `_dashboard/manifest.json` 刷团队大盘。原始 `eval-log.yaml` **不上传**，留在仓库里随代码进 git。

# 附一 · 数字口径与禁区

## 可以直说

- 13 个命令、6 个阶段、3 类事件挂点、8 种项目类型、15 个依赖技能
- 已实测：建 demo 项目跑通 `init` → `/soda:map` → 知识图谱落 14 个产物文件

## 要主动交代口径

- **`ai_dev_hours` 是"人机对话墙钟时间"，不是等效工时**——它包含你思考、读文档、离开的时间。所以"提效倍数 = 人工估值 ÷ 人机对话时长"严格说不是同类量比较。**主动说出来比被问出来好。**
- **轮次口径用 `interventions.length`**，`total_rounds` 字段已弃用（曾出现字段与数组对不上）。

## 绝对不能说

- ❌ 大盘归因类数字（"部门交付周期下降 X%"）——口径一问就崩
- ❌ 声称有 CI/CD —— 实际是手工审查。**这条反而是加分点**，主动讲"我知道边界在哪"
- ❌ "六维审查"的具体维度名 —— 仓库里口径不一致且无定义
- ❌ "AI 替代了人力"

## 待你补充的真实数字

面试时最有分量的三个数，目前还没确认：

1. 部门级覆盖的**项目数 / 人数**
2. 一个真实需求的 `ai_dev_hours` 与 `manual_dev_hours`
3. 日常**真实使用者人数**（不是"装了"）

# 附二 · 必须主动交代的局限（加分项）

主动说局限比被问出来强得多，这几条是真实的：

| 局限 | 准确表述 |
|---|---|
| **门禁只在命中意图关键词时生效** | 不说"impl"而直接说"帮我改这个文件"，门禁不触发。这是**必要妥协**（否则日常问答全被拦） |
| **完全绕过工具链就不受约束** | 不在 Claude Code 里写代码、或直接改文件不提交，整套门禁都不生效。**它约束的是"按流程走的人"，不是"想绕开的人"** |
| **软警告可以一路确认通过** | 时序检查、Git 状态、分支检查都是"回复继续"就过。所以它防的是**遗忘**，不是**故意** |
| **度量的性质是"过程透明"而非"客观审计"** | `interventions` 由 AI 自己总结——红线能保证"如实总结、不事后编造"，防不住"当场记错" |
| **提效归因困难** | 需求难度、人员变动都会干扰，所以只说单案例可追溯的账，不报大盘百分比 |

**一句话收口**：这套机制保证的是"走标准路径时流程不会被无意跳过"，**不是"任何人任何时候都绕不过去"**。

# 附三 · 高频追问速答

| 追问 | 答法要点 |
|---|---|
| 为什么用 `exit 2` 而不是提示词？ | 提示词是"请求别做"，`exit 2` 是协议层"不允许做" |
| 需求变更了怎么发现 Design 过期？ | 比对 ARD 与 Design 的文件修改时间戳，零维护成本 |
| 上下文塞不下怎么办？ | 分层加载：常驻只留薄路由器，图谱按意图路由，源码用完即丢 |
| 为什么用 AST 不用向量检索？ | 结构事实确定、可精确定位 `file:line`、零 token 提取；向量召回有不确定性 |
| 团队统一升级会不会覆盖项目配置？ | 不会。两层配置：技能层每次覆盖，项目层永不覆盖 |
| 硬阻断会不会拖慢开发？ | 所以做了分级，并且给紧急修复留了通道（`/soda:fix`、hotfix 跳过文档检查） |
| AI 写的测试能不能信？ | 所以有独立的 CR 门禁和一致的验收口径，AI 产物全进人工 review |
| 明天禁用所有 AI 工具，团队还转得动吗？ | 能。文档、知识图谱、规范都在仓库里，是项目资产不是 AI 的私有产物 |
