# 智能编排工作流 · 数据采集与上报

> 解析对象：`eval-log.yaml` 的写入链路、`/soda:eval` 的上报链路、以及最终能算出哪些统计指标。
> 配套：[运行时流程解析](./智能编排工作流-运行时流程解析.md)、[八阶段大纲](./智能编排工作流-八阶段大纲.md)、[完整版](./AI落地项目-智能编排工作流.md)

## 一、全景图

```
【采集】                        【存储】              【上报/消费】
各阶段命令                      eval-log.yaml          /soda:eval
  ├─ eval-logger  ──────────→   （7 个数据块）  ──────→ ├─ token 兜底补采
  ├─ token-collect.py ──────→                            ├─ 渲染 HTML → S3
  └─ archive 自评 ──────────→                            └─ merge manifest → S3 大盘
```

**核心解耦**：生产侧只管往一个 YAML 里写，消费侧只管从它读。两者互不知道对方的实现。

---

## 二、采集：七块数据，五个写入方

| # | 数据块 | 写入方 | 写入时机 |
|---|---|---|---|
| 0 | `meta` | eval-logger | **首次创建** eval-log 时（从上下文/git 推断） |
| 1 | `context_checklist` | eval-logger | **仅 ard 阶段**，接收 `$CONTEXT_CHECKLIST` |
| 2 | `stages`（6 个） | eval-logger | 每个阶段结束时 upsert |
| 3 | `rework_log` | eval-logger | 仅 `/soda:sync` 或显式回滚时**追加** |
| 4 | `archive_assessment` | **archive.md 直接写** | 归档自评时（不走 eval-logger） |
| 5 | `token_by_stage` / `token_summary` | **token-collect.py** | 每阶段结束后 / 上传前兜底补采 |

### 2.1 `meta` — 需求元信息（7 字段）

| 字段 | 填写规则 |
|---|---|
| `feature` | 需求目录名 |
| `project` | 仓库根目录名 |
| `branch` | `git rev-parse --abbrev-ref HEAD` |
| `req_id` | **纯数字**单号（Cooper 末段数字 / Jira ticket）；无则空 |
| `source_url` | 完整需求文档 URL |
| `created_at` | 首次创建日期 |
| `owner` | `git config user.name`，可手动覆盖 |

> 红线：`req_id` 禁止填完整 URL，URL 必须放 `source_url`。

### 2.2 `context_checklist` — PRD 完备度（8 项 × 3 字段）

| 8 项 | 每项 3 字段 |
|---|---|
| `prd` / `design_spec` / `tracking_doc` / `translation` / `api_protocol` / `tech_constraints` / `project_context` / `code_context` | `provided`（true / false / null）、`not_applicable`、`note` |

四态渲染：✅ 已就绪 / 🚫 不涉及 / ❌ 缺失 / ❓ 未确认。

### 2.3 `stages` — 六阶段执行数据

**每阶段通用 5 字段**：

| 字段 | 含义 |
|---|---|
| `started_at` | 命令触发时 `date` 取的真实时间（**仅当前值为 null 时写入**） |
| `confirmed_at` | 阶段结束时取的时间 |
| `skills_used` | 本阶段实际加载的 Skill 列表 |
| `interventions` | 逐轮问答清单 |
| `pending_decisions` | 落盘后仍未决的待办原文 |

**阶段专属字段**：

| 阶段 | 专属字段 |
|---|---|
| `plan` | `unconfirmed_tasks` |
| `impl` | `context_supplements`、`files_generated` |
| `cr` | `bugs_found`、`bugs_p0`、`security_blocked` |
| `test` | `coverage_rate`、`defects_found`、`fix_attempts` |

**`interventions[]` 每条 6 字段**：

```yaml
{ round,        # 第几轮
  type,         # clarify / adjust / correct / supplement
  question,     # AI 抛问原文（多题必须保留候选项）
  input,        # 用户原文摘要 ≤120字
  ai_action,    # AI 本轮处理动作 ≤120字
  answered }    # 是否给出实质回答
```

### 2.4 `rework_log` — 返工记录

| 字段 | 口径 |
|---|---|
| `at` | 日期 |
| `cause` | `prd_change` / `api_change` / `cr_finding` / `test_finding` / `user_pivot` |
| `reason` | 一句话原因 |
| `impact` | `light`（1 文件）/ `medium`（2-3）/ `heavy`（4+） |
| `files_changed` | 实际改动文件（**用于计算一次通过率**） |
| `tasks_affected` | 受影响的 Plan 任务编号 |
| `doc_synced` | 同步了哪些文档 |

**触发口径**：只记 `impl.confirmed_at` **之后**的调整。设计阶段的方案迭代不进这里。

### 2.5 `archive_assessment` — 归档自评

| 字段 | 来源 |
|---|---|
| `ai_dev_hours` | **自动**：Σ 六阶段 `(confirmed_at − started_at)` |
| `manual_dev_hours` | 人工：预估自己开发同等需求耗时 |
| `ai_code_ratio` | 人工：AI 生成代码占比 0~1 |
| `first_pass_rate` | **自动** |
| `notes` | 人工 |
| `completed_at` | 归档日期 |

### 2.6 Token 数据

`token_by_stage`：6 阶段 × 4 字段（`input` / `cache_read` / `cache_create` / `output`）

`token_summary`：四项汇总 + `model` + `notes`

**采集实现**：

```
按每个 stage 的 [started_at, confirmed_at + 60s] 构造窗口
  → 扫描 ~/.claude/projects/{project_hash}/*.jsonl
  → 只取 assistant 消息，按 uuid 去重
  → 每条消息只归入一个 stage（break）
  → 覆盖写入（幂等）
```

## 三、采集时点与时序

```
/soda:ard
  ├─ 触发时：取 $STARTED_AT
  ├─ 落盘 ARD
  └─ 阶段末：
       ├─ eval-logger 写 stages.ard + context_checklist
       └─ token-collect.py 采集本阶段 token

/soda:design / plan / test / impl / cr
  └─ 同上（无 context_checklist）

/soda:sync（编码后变更）
  └─ 追加一条 rework_log

/soda:archive
  ├─ 自动算 ai_dev_hours
  ├─ 询问 manual_dev_hours / ai_code_ratio / notes
  └─ 直接写 archive_assessment

/soda:eval
  ├─ Step 1.5 强制补跑 token-collect.py
  └─ 渲染 + 上传
```

## 四、上报链路（6 步）

| Step | 动作 | 产物 |
|---|---|---|
| 1 | 解析项目名 / 分支名 / 需求名（`meta` 优先，git 兜底） | 路径变量 |
| 1.5 | **Token 兜底补采**（强制，幂等） | 更新后的 eval-log |
| 2 | Read eval-log + HTML 模板 | — |
| 3 | inline Python 渲染单文件 HTML | `/tmp/soda-eval-{项目}-{分支}.html` |
| 4 | `upload_to_gift.py` → S3 PUT | `{项目}/{分支}.html` |
| 5 | `update_manifest.py`：GET → merge → PUT | `_dashboard/manifest.json` |
| 6 | 输出两个 URL | 单需求报告 + 团队大盘 |

**上传实现要点**：

- 零依赖：`hmac` + `hashlib` + `base64` + `urllib`，手写 AWS Signature V2
- Content-Type 按后缀自动选
- 对象路径按 `meta` 锚定，切分支后重跑也不漂
- 失败一律软处理：HTML 留 `/tmp`，不落项目目录，不阻断

**原始数据不上传**

`eval-log.yaml` 始终留在 `docs/features/active/{需求}/`，随代码进 git。上传的只是**渲染产物**——所以可重跑、可追溯。

## 五、大盘数据模型

`update_manifest.py` 把一次需求压缩成约 32 个字段的一条记录：

| 类别 | 字段 |
|---|---|
| **身份** | `req_id`、`project`、`branch`、`feature`、`owner`、`archived`、`generated_at` |
| **链接** | `report_url`、`cooper_url` |
| **进度** | `stages_done`、`current_stage` |
| **过程** | `interventions_total`、`interventions_clarify/adjust/correct/supplement`、`rework_count`、`skill_count`、`blockers_count`、`context_completeness` |
| **效率** | `ai_dev_hours`、`manual_dev_hours`、`ai_code_ratio`、`efficiency_x`、`first_pass_rate` |
| **质量** | `cr_bugs_p0`、`cr_bugs_total`、`security_blocked` |
| **成本** | `model`、`token_input_total`、`token_cache_read_total`、`token_cache_create_total`、`token_output_total` |

**去重规则**：按 `req_id` 精确匹配 + `(project, branch)` 兜底清除旧条目；按 `generated_at` 倒序。

## 六、统计指标全表

### 6.1 效率类

| 指标 | 公式 | 来源 |
|---|---|---|
| **AI 开发耗时** | `Σ(confirmed_at − started_at)`，遍历六阶段 | 自动 |
| **提效倍数** | `manual_dev_hours / ai_dev_hours` | 自动 + 人工 |
| **提效百分比** | `(manual − ai) / manual` | 前端折算 |
| **一次通过率** | `(files_generated − 返工文件去重数) / files_generated` | 自动 |
| **各阶段耗时** | 单阶段 `confirmed_at − started_at` | 自动 |

### 6.2 过程类

| 指标 | 公式 | 用途 |
|---|---|---|
| **介入总轮次** | `Σ interventions.length`（**不用 `total_rounds`**） | 衡量交互成本 |
| **澄清数** | `type=clarify` 条数 | 输入材料不足的信号 |
| **调整数** | `type=adjust` 条数 | 方向对但方案要改 |
| **纠错数** | `type=correct` 条数 | AI 理解偏差 |
| **补充数** | `type=supplement` 条数 | 上下文遗漏 |
| **返工次数** | `rework_log.length` | 产物稳定性 |
| **返工影响分布** | `light / medium / heavy` 计数 | 返工严重度 |
| **阻塞数** | `pending_decisions` 中命中关键词的条数 | 协作卡点 |
| **上下文补充次数** | `impl.context_supplements` | impl 期间的补充频率 |
| **未确认任务数** | `plan.unconfirmed_tasks` | 计划的确定度 |
| **技能使用数** | 跨阶段 `skills_used` 去重 | 能力覆盖 |
| **阶段完成数 / 当前阶段** | `stages_done` / `current_stage` | 进度 |

### 6.3 质量类

| 指标 | 公式 |
|---|---|
| **PRD 完备度** | `(provided==true 数 + not_applicable==true 数) / 8` |
| **CR 缺陷数** | `bugs_found`（blocker + warn） |
| **P0 阻断数** | `bugs_p0`（人工） |
| **安全阻断** | `security_blocked`（true/false） |
| **测试覆盖率** | `test.coverage_rate`（允许 null） |
| **测试发现缺陷** | `test.defects_found` |
| **修复迭代次数** | `test.fix_attempts` |

### 6.4 成本类

| 指标 | 公式 |
|---|---|
| **四类 token 总量** | Σ input / cache_read / cache_create / output |
| **Token 成本（美元）** | `input×单价 + cache_create×1.25×单价 + cache_read×0.1×单价 + output×5×单价`（按模型表） |
| **成本（人民币）** | 美元 × 7.3 |
| **AI 代码占比** | `ai_code_ratio`（人工） |

## 七、口径与陷阱（面试必说）

### 7.1 `ai_dev_hours` 不是"等效人力工时"

它是**人机对话的墙钟时长**，包含你思考、读文档、离开去开会的时间。所以：

> "提效倍数 = manual / ai" 严格说**不是同类量比较**。

主动交代这一点，比被追问出来强得多。

### 7.2 轮次口径统一用 `interventions.length`

`total_rounds` 字段**已弃用**（保留写入仅为兼容旧报表）。原因是"手填字段和明细数组对不上"。

### 7.3 `first_pass_rate` 的分母是"生成文件数"

```python
modified_files_set = UNION(所有返工记录的 files_changed) 去重
first_pass_rate = (files_generated − len(modified_files_set)) / files_generated
```

所以它衡量的是"**文件级**一次通过率"，不是"需求级一次通过率"。改一个文件里的一行，整个文件都算返工。

### 7.4 `context_completeness` 把"不涉及"算作完备

```
(provided==true + not_applicable==true) / 总项数
```

这是合理的——不需要埋点的需求不该因为"没提供埋点文档"被扣分。

### 7.5 度量是"过程透明型"，不是"客观审计型"

`interventions` 由 **AI 自己回顾总结**。红线能保证"如实总结、不事后编造"，但**防不住当场记错**。

## 八、数据质量保障机制

| 机制 | 做法 |
|---|---|
| **幂等** | `started_at` 仅在 null 时写；`pending_decisions` 整体覆盖；`interventions` 按 round upsert；token 每次重算覆盖 |
| **防脑补** | 报告数据只能逐字取自 eval-log；缺失即留空，禁止推断补全；有专门测试用例守护 |
| **降级链** | ruamel → pyyaml → 纯正则（无 yaml 库也能跑） |
| **失败不阻断** | token 采集异常静默退出；上传失败保留 `/tmp` |
| **自动/人工分离** | 客观数据自动采集，主观数据人工填，字段注释标注 `[自动]` / `[人工]` |

---

## 九、一句话总结

> 采集侧用**一个 YAML** 装七块数据（元信息、输入完备度、六阶段过程、返工、自评、token），由三个写入方分工；上报侧把它渲染成 HTML 和 32 字段的大盘数据推进 S3。整套设计的核心取舍是——**客观数据自动采、主观数据人工填、缺失一律留空，宁可没有，不可编造**。
