> 八个阶段的详细大纲？见 [智能编排工作流-八阶段大纲.md](./智能编排工作流-八阶段大纲.md)。

## 1. 项目定位

这个项目可以定义为：

`一套把研发流程本身编码成 AI 行为约束的命令驱动工作流，覆盖需求分析、技术设计、开发计划、测试方案、编码实施、代码审查、归档沉淀七个阶段，用阶段门禁保证流程不可跳过，用评测体系度量提效结果。`

它不是一个"帮团队用上 AI 工具"的推广项目，也不是一个通用 Agent 框架。它的核心命题是：

`不是让 AI 更聪明，而是给它一个工程师的工作环境。`

## 2. 为什么这个项目适合面试介绍

- 它回答的是"重构研发流程"，而不是"用了哪些 AI 工具"，天然区别于"我们用了 Cursor"这类回答。
- 需求侧、设计侧、工程侧三块能力都能体现：流程抽象、门禁设计、度量体系。
- 门禁的硬/软分级、上下文分层加载、评测口径设计，都能被追问三层以上而不空。
- 有真实迭代痕迹：近三个月持续迭代，跨项目统一下发。

面试里最稳的表达不是"AI 帮我们提效了"，而是：

`我把流程编码成 AI 必须执行的通道，用门禁保证它不跳过、用数据证明它有效。`

## 3. 核心设计理念

### 3.1 命令模式是唯一触发方式

所有阶段都通过显式命令触发（如 `/soda:ard`、`/soda:impl`），**没有自动模式**。除了命中命令，AI 直接回复，不加载任何 Skill。

这样做的理由：

- **可控**：AI 不会在执行到一半时自行决定进入下一阶段。
- **可审计**：一次需求走了哪些阶段、每个阶段做了什么，全部有落盘记录。
- **责任边界清晰**：是"我让它做"还是"它自己要做"，在日志里分得清。

### 3.2 文档先行不可绕过

工作流规定：**文档不落盘不能进下一阶段，文档没确认不能写代码**。

这条不是靠提示词约束的，而是靠物理门禁：缺 Design 或 Plan 时，写代码前的前置钩子直接 `exit 2` 硬阻断。

### 3.3 AI 负责提速和补全，人负责边界和正确性

每个阶段的关键节点都有 `HARD STOP`，必须等用户确认才继续。并且有一条"确认隔离原则"：用户说"OK"只代表当前 Skill 完成，不代表后续 Skill 可以跳过。

## 4. 三层结构

| 层 | 位置 | 职责 |
|---|---|---|
| **编排层** | `commands/soda/*.md`（13 个命令） | 每个命令是一段 Step 剧本，定义该阶段按什么顺序做什么 |
| **约束层** | `RULE.md` + `hooks/` + `docs/rules/` | 决定 AI 能不能动：触发规则、阶段门禁、项目红线 |
| **记忆层** | `docs/knowledge/` | 知识图谱、经验库、术语表、技术栈快照，让 AI 知道项目长什么样 |

三层的关系：编排层负责"做什么"，约束层负责"能不能做"，记忆层负责"基于什么做"。

## 5. 一个需求的完整生命周期

```
一次性：bash scripts/init-project.sh   ← 装环境、拉依赖、注入命令与钩子
                    ↓
  ┌──────────────── 主链路（每步都要确认才走下一步） ────────────────┐
  │ /soda:ard → /soda:design → /soda:plan → /soda:test → /soda:impl  │
  │                                                       ↓          │
  │                                        /soda:cr → /soda:archive │
  └──────────────────────────────────────────────────────────────────┘
                    ↓
        archive 自动触发 /soda:map --update（图谱与代码对齐）
                    ↓
                    /soda:eval（出评测报告 → 传对象存储 → 刷团队大盘）
```

旁路命令：

| 命令 | 用途 |
|---|---|
| `/soda:map` | 扫描项目生成 AST 知识图谱 |
| `/soda:sync` | 代码 + 文档联动更新（需求变更时先同步文档再动代码） |
| `/soda:fix` | Bug / 性能排查修复 |
| `/soda:mock` | 生成接口 Mock |
| `/soda:exp` | 提炼经验写入经验库 |
| `/soda:eval` | 生成效率评测报告并上传 |

**关键点：`docs/features/active/{需求名}/` 是整个流程的状态机。** 每个阶段的产物都落在这里（ARD / Design / Plan / Test / progress.md / eval-log.yaml），下一个阶段读上一个阶段的产物。

所以在这套体系里，**文档不是副产物，而是流水线的传送带**——这一点是理解全局的关键。

## 6. 每个阶段的固定骨架

六个文档生成命令几乎共用同一套 Step 序列：

| Step | 做什么 | 硬约束 |
|---|---|---|
| **Step -1** | 确认项目类型 + 收集输入 | `/soda:ard` 没有 PRD 输入就 HARD BLOCK，禁止继续 |
| **Step 0** | 装载上下文（知识图谱探针） | 图缺失时 HARD STOP，建议先建图；用户可回"跳过"降级 grep |
| **Step 1** | 按配置顺序执行 input Skill | 每个 Skill 单独确认，不得批量跳过 |
| **Step 1.5 / -0.5** | 执行 inputSlot 跨阶段切片 | 自门控：上游无产出则自行跳过 |
| **Step 2** | 读取模板 | 优先级：`config.output` > `project.type` 默认 > 文件嗅探 |
| **Step 3** | 中文润色（去机器腔、去填充词） | 固定动作，每份文档都过 |
| **Step 3.5** | 输出大纲等用户确认 | **确认前禁止写入任何文件** |
| **Step 4-5** | 落盘 + 更新 progress.md | 文件名、路径、章节结构全部固定 |
| **末步** | 写入 eval-log | 标注"必须执行，不得跳过" |

### 6.1 各阶段的独有动作

| 阶段 | 独有设计 |
|---|---|
| `ard` | 蒸馏就绪校验（8 项输入清单，软约束不阻断）；影响域深度追踪（改动入口 / 传播链 / 高风险节点） |
| `design` | 影响域作为强约束：改动清单不可越界，高风险节点必须给隔离方案 |
| `plan` | 高风险节点任务排到最后或加 feature flag；共享模块改动单独拆 Task 评估回归 |
| `test` | 按 `tech.yaml` 的 i18n 语言列表生成验证清单，不硬编码语言 |
| `impl` | 强制加载 `docs/rules/` 三份规约，建立三张检查表逐任务预检 |
| `cr` | 六级分级（BLOCKER / WARN / NIT），score = 10 − BLOCKER×3 − WARN×1 − NIT×0.3 |
| `archive` | diff 分类（api / db / arch 变更）→ 增量刷新图谱 → tech.yaml 三向对账 |

### 6.2 `.soda:impl` 的逐任务循环

编码实施是唯一按任务粒度循环的阶段，节奏固定为：

```
标记 [🔄] → 规范合规预检 → Read 目标文件 → 精准实施 → 标记 [x] → 输出进度
```

其中"规范合规预检"对照三张表：

- **FORBIDDEN_LIST**（来自 `forbidden.md`）→ 命中即 HARD BLOCK，不写代码，等指示
- **TECH_ALLOWED**（来自 `tech-selection.md`）→ 引入未列出的依赖必须停下确认
- **CODE_STYLE**（来自 `code.md`）→ 每行代码输出前强制对照

并且规定了规范优先级：**`docs/rules/` 高于 Design 规格、高于 Plan 描述、高于任何 Skill 建议**。

## 7. 运行时真正拦人的三道门

控制流不在剧本里，在钩子（hooks）。三个挂点、三种力度：

| 挂点 | 触发时机 | 检查内容 | 力度 |
|---|---|---|---|
| `UserPromptSubmit` | 每条用户消息前 | 缺 Design / Plan | **exit 2 硬阻断** |
| `PostToolUse`（Write/Edit） | 每次写文件后 | `eval()` / `new Function` / `v-html` / 硬编码密钥 / `innerHTML` / `document.write` | **exit 2 硬阻断** |
| | | `console.log` / `debugger` / 硬编码中文 / `TODO` / 硬编码 `http://` | 软警告 |
| `PreToolUse`（git commit/push） | 提交前 | CR 结论为 fail / 暂存增量含敏感信息 / 内网 IP / 私钥 | **exit 2 硬阻断** |
| | | CR 后代码有变更（结论过期）/ 非 fix 分支且无 CR 记录 | 软警告 |

外加剧本层的 `HARD BLOCK`：命中 `docs/rules/forbidden.md` 立即停止。

### 7.1 三种力度合起来才是完整设计

- **硬阻断**：涉及安全、流程完整性、不可逆风险的，直接拦停。
- **软警告**：提示但不拦，把判断权留给人。
- **静默通过**：无问题时脚本完全不输出，作者注释写的是"保持 Claude 上下文干净"。

这个分级比"全拦"或"全不拦"都难做——**面试里这是最能体现判断力的地方**。

### 7.2 代码审查的分级与模式

- 分级：`BLOCKER`（硬阻断、流程终止）/ `WARN`（有条件通过，等用户确认）/ `NIT`（建议）
- 结果落盘为结构化的审查结论文件，含 `blockerCount` / `warnCount` / `nitCount` / `score` / `result` / `headCommit`
- 模式：默认只报 BLOCKER（适合日常提测）/ 全量六维审查 / 只审高风险文件 / 复审上次 BLOCKER / 紧急修复跳过审查

## 8. 评测与数据闭环

这是整套体系里最容易被低估的部分。

### 8.1 每个阶段结束必须落数据

每份文档落盘后，AI 必须调用评测记录器把本阶段数据写入 `eval-log.yaml`：

```yaml
meta                  需求号 / 项目 / 分支 / owner
context_checklist     PRD 完备度 8 项（就绪 / 缺失 / 不涉及 / 未确认 四态）
stages[6]             每阶段：started_at、confirmed_at、skills_used、
                      interventions[]、pending_decisions[]
rework_log[]          返工归因（产品变更 / 接口变更 / CR 发现 / 测试发现 / 方向调整）
archive_assessment    ai_dev_hours（自动）/ manual_dev_hours（人工）/ ai_code_ratio
token_by_stage        各阶段 token 消耗
```

### 8.2 介入轮次的四分类

这是设计得比较巧的一点——不是记"用户打断了几次"，而是按性质分类：

| 类型 | 含义 |
|---|---|
| `clarify` | 澄清：信息不足，需要问清楚 |
| `adjust` | 调整：方向对但方案要改 |
| `correct` | 纠错：AI 理解错了 |
| `supplement` | 补充：遗漏了上下文 |

**这四类反过来就是流程哪里设计得不好的证据。** 比如 `clarify` 多说明输入材料不足，`correct` 多说明提示或约束不到位。

### 8.3 核心指标与口径

| 指标 | 口径 | 采集方式 |
|---|---|---|
| AI 开发耗时 | 六个阶段 `Σ(confirmed_at − started_at)` | 自动 |
| 提效倍数 | `manual_dev_hours / ai_dev_hours` | 人工填 manual + 自动算 ai |
| AI 产物一次通过率 | `(生成文件数 − 返工涉及文件去重数) / 生成文件数` | 自动 |
| PRD 完备度 | `(就绪项 + 不涉及项) / 总项数` | 阶段采集 |
| Token 消耗与成本 | 按各阶段时间窗口统计，按模型单价折算 | 自动 |

### 8.4 给度量本身设的防幻觉红线

评测命令里有一条最高优先级红线：

> 报告里的一切过程数据只能逐字取自 `eval-log.yaml`。缺失字段一律按"未开始 / — / 待归档"渲染，**不准**从 ARD/Design/Plan/Test 文档、git 提交时间、文件修改时间、对话历史去推断、补全或编造任何过程数据。

唯一允许的计算是对**已存在字段**做聚合。

并且专门有一条测试用例守着这条红线。**这一点在面试里非常有说服力：不仅度量了 AI，还给度量本身设了防幻觉机制。**

### 8.5 Token 采集的实现方式

- 按每个阶段的 `[started_at, confirmed_at + 60s]` 作为时间窗口
- 从本地会话日志目录按项目路径哈希定位 jsonl 文件
- 只统计 assistant 消息，按消息 id 去重（避免流式分片重复计数）
- 一条消息只归入一个阶段
- 解析链有降级：完整 yaml 库 → 简化 yaml 库 → 纯正则兜底
- **任何异常静默退出，绝不阻断主流程**

## 9. 知识图谱闭环

### 9.1 建图

静态分析管道零 token 提取结构事实，再用模型读码补证：

```
nav-parser（解析依赖/别名） → graph-cluster（聚类，识别枢纽） 
→ deep-analyzer（状态机/分支路由候选） → 产物落 docs/knowledge/navigation/
```

产物包括文件依赖图、导出函数调用关系、组件引用、聚类与枢纽、健康报告、增量索引。

### 9.2 用图

需求分析、技术设计、排障、代码审查在查代码时**优先读图**：先读路由索引定位业务域，再进具体图节点；**只有在图谱未覆盖时才降级 grep**，并且必须指定具体路径，禁止全仓库盲扫。

### 9.3 保鲜

- 归档时**自动**触发增量刷新，按基线提交做 diff，只刷受影响节点及其 1-2 跳反向依赖，几秒完成
- 需求分析前有新鲜度探针：图落后超过 20 个文件变更就提示先刷新，用户可选择"继续（接受偏差）"或"刷新"

### 9.4 分层上下文加载

这是配套的上下文成本控制设计：

| 层级 | 内容 | 加载时机 |
|---|---|---|
| Tier 1 规则层 | 项目铁律 + 薄路由器 | 常驻，无需手动读取 |
| Tier 2 知识层 | 全项目图 + 按域深档 + 术语表 | 命中意图后按需读取，**绝不全量加载** |
| Tier 3 源码层 | 具体源文件 | 执行任务时按需读，用完即丢 |

所以初始化时入口文件只写入一行规则引用，注释写着"避免每次新对话固定吃掉大量上下文"。

## 10. 规模化分发机制

### 10.1 两层配置

| 层级 | 内容 | 管理方 | 重新初始化的行为 |
|---|---|---|---|
| **Skill 层** | 工作流本体、依赖 Skill、命令文件 | 工作流维护者 | **每次覆盖** → 保证统一升级 |
| **项目层** | 工作流配置、项目编码规范、知识图谱 | 项目团队 | **永不覆盖** → 保证个性化 |

**核心原则：重新初始化时，项目层文件永不覆盖，Skill 层文件每次更新。**

下发新版 = 各项目重跑一次初始化脚本，项目自己的配置、规范、图谱完全不受影响。这是"规模化"三个字真正的答案——**统一升级和项目个性化不冲突**。

### 10.2 一键初始化的动作

1. 检测项目类型（前端 / Java / Go / Node / Python / PHP / 全栈，共 8 种），选择对应模板
2. 拉取依赖 Skill 与模板
3. 按两层规则写入或覆盖文件
4. 注入 AI 行为规则入口
5. 安装 git 钩子（分支切换 / 合并后校验配置）
6. 把命令写入命令目录，并按项目配置为每个命令注入 Skill 加载顺序

### 10.3 配置变更自动生效

配置文件的哈希被记录在锁文件里，git 钩子比对发现变更就自动重跑初始化，无需人工记得。

## 11. 工作流自身也有测试

提效工具本身的质量同样被保障，分三层：

| 套件 | 覆盖内容 |
|---|---|
| 工作流集成测试 | 完整正向流水线、文档门禁阻断链路、代码质量门禁、提交门禁、变更信号检测、边界与容错、安装路径解析、文档契约一致性、上传契约、评测脚本行为、字段契约、防脑补红线 |
| 钩子边缘测试 | 各类文件后缀与豁免、暂存区隔离扫描、安全契约回归 |
| 知识图谱健康度测试 | 产物完整性、基线跨文件一致性、图谱质量（证据覆盖率 / 自环节点 / 未解析比例）、路由字段 |

其中一部分测试是**真正执行脚本**（包括端到端跑上传逻辑），另一部分是**静态契约校验**——因为很多约定是不可执行的文档契约，只能用静态检查防止漂移。

**这一点值得单独讲：它说明"给 AI 用的工具"也被当作正经工程对待。**

## 12. 关键设计取舍

这些是面试里最容易被追问、也最能体现思考深度的点。

| 取舍 | 选择 | 理由 |
|---|---|---|
| 命令驱动 vs 自动模式 | 命令驱动 | 可控、可审计、责任边界清晰 |
| 流程约束 vs 提示词约束 | 物理门禁 | 提示词会被忽略，脚本 `exit 2` 不会 |
| 硬阻断 vs 软警告 | 分级 | 安全与流程完整性问题硬拦，风格问题提示，判断权留给人 |
| AST 知识图谱 vs 向量检索 | AST | 结构事实确定、可精确定位到文件行号、零 token 提取；向量召回有不确定性 |
| 常驻上下文 vs 按需加载 | 分层按需 | 常驻只留薄路由器，避免每次对话固定消耗上下文 |
| 统一升级 vs 项目个性化 | 两层分离 | 前者保统一，后者保落地 |
| 全自动采集 vs 人工填报 | 能自动则自动 | 时间戳、文件数、token 自动；主观工时与代码占比人工 |

## 13. 当前已知问题（复习时注意，别在面试里说错）

整理时核对到的几处不一致，讲之前建议先统一口径：

1. **审查维度口径冲突**：代码审查命令里写"六维审查"，说明文档里写"五维质量审查"，而六维的具体维度名在工作流仓库内没有定义（审查能力来自外部依赖 Skill）。被追问"哪六维"会当场卡住。
2. **测试覆盖描述过时**：入口说明文档写的测试编号范围（W1-W8 / S1-S4 / M1-M7）已落后于实际（实际已扩展到 W17 / S5，其中 W7 已移除但编号保留）。
3. **版本号不同步**：技能描述文件里的版本号与遥测上报里写的版本号不一致。
4. **文档渲染问题**：命令文件里有一处内容重复（同一段落写了两遍，第二遍残留了 markdown 标记）。
5. **凭证硬编码**：对象存储的访问凭证被硬编码在测试文件里并提交进了版本库，与"凭证不进仓"的规范相悖。**建议轮换凭证并改为读环境变量，测试只断言"读到了环境变量"。**

## 14. 面试表达要点

### 14.1 一分钟版

`我主导建设并部门级下发了一套命令驱动的 AI 研发工作流。它把需求分析、设计、计划、测试、编码、审查、归档七个阶段，编码成 AI 必须执行的命令通道；用钩子在关键节点做门禁，缺文档不许写代码、提交前必须过审查和安全扫描；同时给每个阶段采集耗时、介入轮次、返工原因和 token 成本，形成可追溯的评测数据。核心思路不是让 AI 更聪明，而是给它一个工程师的工作环境。`

### 14.2 展开时可以往这几个方向挖

- 为什么用物理门禁而不是提示词约束
- 硬阻断和软警告是怎么划分的，划分依据是什么
- 上下文分层加载解决了什么问题
- 为什么用 AST 知识图谱而不是向量检索
- 评测指标为什么这么选，怎么排除干扰因素
- 两层配置怎么解决"统一升级"和"项目个性化"的矛盾

### 14.3 容易答偏的地方

- 只罗列工具名（"我们用了 Claude Code / Cursor"），讲不出流程设计
- 把"提效"说成感受，拿不出可追溯的证据
- 声称有 CI/CD（实际是手工审查）——**这条反而是加分点，主动讲"我知道边界在哪"**
- 报来源不明的大盘百分比，被追问口径就崩
- 把"AI 自动完成"当卖点，实际上整套设计的重点恰恰是**人负责边界和正确性**
