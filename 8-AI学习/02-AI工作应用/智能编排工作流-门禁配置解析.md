# 智能编排工作流 · 门禁配置解析

> 解析对象：项目级 `.claude/settings.json`（由 `scripts/shell/hooks-init.sh` 生成）
> 配套阅读：[智能编排工作流-速览卡.md](./智能编排工作流-速览卡.md)、[AI落地项目-智能编排工作流.md](./AI落地项目-智能编排工作流.md)、[智能编排工作流-初始化脚本解析.md](./智能编排工作流-初始化脚本解析.md)、[智能编排工作流-运行时流程解析.md](./智能编排工作流-运行时流程解析.md)

## 0. 这份文件是什么

它不是普通配置，而是 **Claude Code 的钩子协议声明**——决定"什么时机、执行什么、能不能拦停"。

由初始化脚本生成，文件内 `_doc` 字段声明"勿手动修改路径"。它是整套工作流里"物理门禁"的落点：脚本层的拦截能力，全部靠这份声明才被挂上。

## 1. 顶层三个字段

```json
{
  "_doc": "...",              // 注释字段，运行时忽略，纯给人看
  "disableAllHooks": true,    // 见 §6，有一个需要实测确认的点
  "hooks": { ... }            // 三类事件挂点
}
```

## 2. 三个事件挂点的语义差异

理解全局的关键，就在这三行的区别上：

| 事件 | 触发时机 | 能拦什么 | 本配置的用途 |
|---|---|---|---|
| **`UserPromptSubmit`** | 用户每发一条消息、**模型还没开始处理**时 | 整个请求 | 编码前置检查 |
| **`PreToolUse`** | 工具调用**执行前** | 这一次工具调用 | 提交门禁 |
| **`PostToolUse`** | 工具调用**执行后** | 拦不住已发生的，只能告警 | 代码快扫、文档质检 |

**最要紧的是第一行**：`UserPromptSubmit` 在模型开始思考之前就已经跑完了。

这解释了"文档先行"为什么挂在这里——如果挂在写文件前，那时模型**已经决定**要写代码了，属于事后纠正；挂在消息入口，是在"要发车"这个念头出现的当下就拦，还能把"你还缺哪份文档"提前喂回去。

## 3. 单个条目的字段逐个拆

结构：`事件 → [ { matcher, hooks: [ {hook定义}, ... ] } ]`

外层用 `matcher` 筛，内层可以挂**多个 hook 并行执行**（本配置的提交门禁就是 shell + agent 两个一起跑）。

字段含义引运行时 schema 的描述原文（从 `claude` 可执行文件里提取，非推测）：

| 字段 | 运行时描述 | 作用 |
|---|---|---|
| `matcher` | — | 匹配工具名，正则。`"Write\|Edit"` 只在这两个工具后触发 |
| `if` | — | 更细的条件过滤，如 `Write(**/ARD-*.md)`、`Bash(git commit*)` |
| `type` | — | `"command"` / `"agent"` / `"prompt"` / `"http"` / `"mcp_tool"`，运行时对应五套 schema |
| `command` | — | `type=command` 时执行的 shell |
| `prompt` | *"Prompt to evaluate with LLM. Use `$ARGUMENTS` placeholder for hook input JSON."* | `type=agent/prompt` 的指令，`$ARGUMENTS` 会被替换成工具调用的 JSON |
| `model` | *"Model to use for this prompt hook. If not specified, uses the default small fast model."* | 本配置显式指定了 haiku |
| `timeout` | *"Timeout in seconds..."* | 秒，本配置用了 10 / 15 / 30 / 60 / 90 五档 |
| `statusMessage` | *"Status message to display in spinner while hook runs"* | 运行时 UI 转圈时显示的文字 |
| `async` | *"If true, hook runs in background without blocking"* | 后台执行，不阻塞主流程 |
| `asyncRewake` | *"If true, hook runs in background and wakes the model on exit code 2 (blocking error). **Implies async**."* | 后台跑，但 **exit 2 时把模型叫醒** |
| `once` | *"If true, hook runs once and is removed after execution"* | 本配置未使用 |

### 3.1 `asyncRewake` 是这份配置里最精妙的一处

运行时还配了两个内部字段来解释它的行为：

- `rewakeMessage`：*"Custom prefix for the system-reminder shown to the model when an asyncRewake hook exits with code 2"*
- `rewakeSummary`：*"One-line summary shown to the user in the terminal when an asyncRewake hook exits with code 2. Defaults to 'Stop hook feedback'."*

`after_code_scan.sh` 挂在 `PostToolUse` + `asyncRewake` 上，实际行为是：

```
写完代码 → 后台跑扫描（不阻塞，开发者感觉不到卡顿）
              ↓
        发现问题 → exit 2 → 唤醒模型，把扫描输出喂给它
              ↓
        没问题  → exit 0 → 完全静默，不留任何痕迹
```

**"平时零成本、出事才介入"** —— 这就是它要用异步的原因。

## 4. 退出码语义

| 退出码 | 含义 |
|---|---|
| `0` | 通过。若同时无输出，模型和用户都看不到任何东西 |
| `2` | **阻断性错误**。宿主拦截这次动作（或唤醒模型），并把输出回灌给模型 |

这是整套门禁能"物理拦截"的根本：**不是提示词请求模型别做，而是协议层不允许这次调用完成**。

## 5. 四个钩子详解

### ① `UserPromptSubmit` → `before_impl_check.sh`

唯一**没有 `matcher`** 的条目（匹配的不是工具，是人类输入）。

- 先做意图识别：消息里没有 `impl / 发车 / 开始编码 / 实施` 等关键词 → `exit 0`，**50ms 内静默退出**
- 命中 → 检查 Design / Plan / ARD 是否存在、ARD 与 Design 的时序、Git 状态、分支、构建配置
- 缺 Design 或 Plan → **`exit 2` 硬阻断**
- 其余（ARD 缺失、工作区脏、在 main 分支）→ `exit 0` + 打印警告

### ② `PostToolUse` / `matcher: Write|Edit` → `after_code_scan.sh`

`async: true` + `asyncRewake: true` + `timeout: 15`。

- 硬阻断（exit 2）：`eval()`、`new Function()`、硬编码密钥、`v-html` 绑变量、`innerHTML`、`document.write`
- 软警告（exit 0）：`console.log`、`debugger`、硬编码中文、`TODO`、硬编码 `http://`
- 只扫 `.js / .vue / .ts / .jsx / .tsx`，其他文件直接静默退出

### ③ `PostToolUse` / `matcher: Write` → 两个 `agent` 型钩子

用 `if` 区分目标，一个管 ARD、一个管 Design：

| 条件 | 读取的规则文件 | 检查内容 |
|---|---|---|
| `Write(**/ARD-*.md)` | `hooks/after_ard.md` | 需求覆盖度、边界完整性 |
| `Write(**/Design-*.md)` | `hooks/after_design.md` | 架构完整性、影响域高风险节点隔离 |

模型固定 `claude-haiku-4-5-20251001`，`timeout: 90`。

这是**语义层门禁**：机械层查不了的（"需求覆盖是否完整""架构是否自洽"），交给小模型按 markdown 规则判。

### ④ `PreToolUse` / `if: Bash(git commit*)` → 两个钩子并行

同一个条件下挂了两个钩子，**一个机械、一个语义**——这是本文件最能说明设计意图的地方：

| 顺序 | 类型 | 职责 |
|---|---|---|
| 1 | `command` | `before_commit_check.sh`：CR 状态为 fail → 阻断；暂存增量含敏感信息 / 内网 IP / 私钥 → 阻断 |
| 2 | `agent` | 读 `hooks/before_commit.md`，做 hotfix 场景识别、CR 状态校验、headCommit 一致性检查 |

注意 agent 那条 prompt 里的一句：

> *"注意：跳过 Step 3（敏感信息扫描），该步骤已由 Shell 脚本独立执行，无需重复。"*

**职责显式去重**——避免机械层和语义层重复做同一件事，既省 token，也避免两层给出不一致的结论。

## 6. ⚠️ 一个需要实测确认的点：`disableAllHooks`

配置里自己的注释写的是：

> "先全局关闭 hook 自动发现，再逐条显式声明要装的" —— 白名单式配置

但从 `claude` 运行时里提取到的 schema 描述原文是：

> **`disableAllHooks`：`"Disable all hooks and statusLine execution"`**

运行时里的相关告警文案还有：

```
Skipping hooks for X due to 'disableAllHooks' managed setting
To re-enable hooks, remove "disableAllHooks" from settings.json or ask Claude.
Status line is configured but disableAllHooks is true
```

运行时代码里存在两套作用域（普通 settings 与 `policySettings` 托管配置），检查逻辑互相交错，**从压缩后的代码里无法确定"项目级设为 true 是否会连同自己声明的 hook 一起关掉"**。

这件事必须实测，因为两种结果差异极大：

| 如果实际语义是…… | 后果 |
|---|---|
| 只关闭自动发现 | 门禁正常工作，符合作者意图 |
| 真的关闭全部 hook | **整套门禁在实际使用中根本不触发** |

> 注意：直接调用钩子脚本能拦人，**但这不能证明宿主会调用它们**——两者是不同层面的事。

**30 秒验证法**：在项目里开一个 Claude Code 会话，让它写一个含 `eval(` 的 js 文件。

- 出现 `📋 代码安全快扫...` 的转圈提示并被拦 → hook 生效
- 毫无反应 → `disableAllHooks` 把它一起关了

或者更直接：在该会话里执行 `/hooks`，看列出的钩子状态。

## 7. 一句话总结

> 这份配置把研发流程的约束**从提示词搬到了协议层**：`UserPromptSubmit` 拦"发车"，`PreToolUse` 拦"提交"，`PostToolUse` 在后台静默巡检、只在该报警时才把模型叫醒；能用正则判的走 shell，判不了语义的交给 haiku；两者同条件并行，并用 prompt 显式划分职责边界。
