# 智能编排工作流 · 八阶段大纲

> 本文按执行顺序拆解 8 个阶段：目标、输入、步骤、产物、停点、落盘数据。
> 配套：[速览卡](./智能编排工作流-速览卡.md)、[完整版](./AI落地项目-智能编排工作流.md)、[初始化](./智能编排工作流-初始化脚本解析.md)、[门禁](./智能编排工作流-门禁配置解析.md)、[运行时](./智能编排工作流-运行时流程解析.md)、[数据采集与上报](./智能编排工作流-数据采集与上报.md)

## 总览

| # | 阶段 | 命令 | 一句话 | 产物 |
|---|---|---|---|---|
| 1 | 需求分析 | `ard` | 把模糊需求变成可验证的基线 | `ARD-{需求}.md` |
| 2 | 技术设计 | `design` | 把需求变成可实施的技术方案 | `Design-{需求}.md` |
| 3 | 开发计划 | `plan` | 把方案拆成可执行任务 | `Plan-{需求}.md` |
| 4 | 测试方案 | `test` | 定义"怎么证明没改坏" | `Test-{需求}.md` |
| 5 | 编码实施 | `impl` | 按任务逐条落地 | 代码 + `progress.md` |
| 6 | 代码审查 | `cr` | 提交前最后一道把关 | `.claude/cr-status.json` |
| 7 | 归档 | `archive` | 收口并让知识可复用 | `completed/` + 经验 + 图谱 |
| 8 | 评测 | `eval` | 把过程数据变成可读报告 | HTML + 大盘 |

**阶段之间不自动流转**，每步手动触发。唯一例外：`archive` 会自动触发 `/soda:map --update`。

---

## 阶段 1 · 需求分析 `/soda:ard`

**目标**：把模糊需求变成"可执行、可验证"的基线，并盘清改动会波及哪里。

**输入**：Cooper 链接 / 需求描述文本（≥3 行）；为空直接 HARD BLOCK。

**执行步骤**

| Step | 做什么 | 停点 |
|---|---|---|
| **-1** | 确认项目类型；收集 PRD（三种分支）；执行**蒸馏就绪校验 8 项** | 无有效输入 → **HARD BLOCK** |
| **0.0** | **知识图谱探针**：检查图是否存在 → 新鲜度（落后 >20 文件提示）→ 读路由/深档/图节点 → 输出探针报告 | 图缺失 → **HARD STOP**（可回"跳过"降级 grep） |
| **0.1** | **影响域深度追踪**：改动入口 / 传播链 / 高风险节点 | 无 |
| **1** | 按 `commands.ard.input` 执行 Skill（通常 `brainstorming`） | **每个 Skill 单独确认** |
| **1.5** | 执行 `inputSlot` 跨阶段切片（如有） | 每个切片单独确认 |
| **2** | 读模板 `ARD-模版.md` | 无 |
| **3** | 中文润色（Humanizer） | 无 |
| **3.5** | 🛑 **输出大纲等确认** | **确认前禁止写文件** |
| **4** | 建需求目录 + 落盘 ARD + `progress.md` | 无 |
| **5-6** | 推进 `progress.md` → 写 eval-log | 末步"必须执行" |

**产物**：`docs/features/active/{需求}/ARD-{需求}.md`、`progress.md`、`eval-log.yaml`

**落盘数据**：`stages.ard` + **`context_checklist` 8 项**（唯一在 ard 阶段采集的块）

**下游意义**：影响域分析是 Design 与 Plan 的**强约束输入**——Design 只能在改动清单内设计，高风险节点必须给隔离方案。

---

## 阶段 2 · 技术设计 `/soda:design`

**目标**：把需求转成可实施的技术方案。

**输入**：ARD（默认读 `active/` 下最新）。

**执行步骤**

| Step | 做什么 |
|---|---|
| **-1** | 按 `commands.design.input` 加载 Skill（gattaran：`field-config-designer`） |
| **-0.5** | 执行 inputSlot 切片（自门控：上游无产出则跳过） |
| **0** | 确定项目类型 |
| **1** | **读 ARD + 影响域**，提取三条约束：改动清单（不可越界）、高风险节点（必须隔离）、下游传播链（必须验证兼容） |
| **2** | 读模板（Fe / Server / Gattaran 三选一） |
| **3** | 技术约束检测：读 `docs/rules/`；查代码**优先知识图谱，grep 为次选**（且禁止全仓库盲扫） |
| **4** | 中文润色 |
| **5** | 落盘 + 更新 `progress.md` |
| **6** | 写 eval-log |

**产物**：`Design-{需求}.md`

**注意**：`design.md` **没有显式的 Step 3.5 大纲确认**，润色后直接落盘（见文末"跨阶段观察"）。

---

## 阶段 3 · 开发计划 `/soda:plan`

**目标**：把方案拆成带依赖和工时的可执行任务。

**输入**：Design + ARD 影响域。

**执行步骤**

| Step | 做什么 |
|---|---|
| **-1 / -0.5 / 0** | 加载 Skill / 切片 / 确定类型 |
| **1** | 读 Design + 影响域，按风险排布任务：高风险节点 → 排末尾或加 feature flag；纯新增 → 可并行提前；共享模块改动 → 单独拆 Task 评估回归 |
| **2** | 读模板，每个任务用 `- [ ]` + 估算工时 + 前置依赖 |
| **3** | 中文润色 |
| **4** | 落盘 + 更新 `progress.md` |
| **5** | 写 eval-log（含 `unconfirmed_tasks`） |

**产物**：`Plan-{需求}.md`

**下游意义**：`impl` 严格按这份 Plan 的 `- [ ]` 逐条执行，`--from` 断点也基于任务编号。

---

## 阶段 4 · 测试方案 `/soda:test`

**目标**：在写代码前定义"怎么证明没改坏"。

**输入**：ARD + Plan。

**执行步骤**

| Step | 做什么 |
|---|---|
| **-1** | 加载 `test-driven-development` |
| **0** | 确定项目类型 |
| **1** | 读 ARD + Plan |
| **2** | 读模板；用例用 `[ ]` 标记、`TC-01` 连续编号；i18n 章节**按 `tech.yaml` 的语言列表生成**，不硬编码 |
| **3** | 中文润色 |
| **4** | 落盘 + 更新 `progress.md` |
| **5** | 写 eval-log（`coverage_rate` / `defects_found` / `fix_attempts` 允许 null） |

**产物**：`Test-{需求}.md`

**差异**：`test` 没有 `-0.5` inputSlot 步骤（与 design / plan 不同）。

**测试侧重**：前端→状态机、多端兼容、i18n、埋点；后端→接口契约、幂等/事务、P99、降级、安全。

---

## 阶段 5 · 编码实施 `/soda:impl`

**目标**：按 Plan 逐任务落地，每步都过规范预检。

**输入**：Plan + Design；支持 `--from <任务编号>` 断点恢复。

**执行步骤**

| Step | 做什么 | 关键约束 |
|---|---|---|
| **-1** | 确定类型 | — |
| **0** | 加载 `commands.impl.input`（gattaran：`mid-backend-standards`） | — |
| **0.6** | 加载 inputSlot 切片 | 自门控 |
| **0.5** | **强制 Read `docs/rules/` 三份**：`code.md` / `tech-selection.md` / `forbidden.md` | 占位符 ≥3 处 → 软警告等确认 |
| **1** | 定位 Plan + Design；跳过 `[x]` 与 `--from` 之前的任务 | — |
| **2** | 输出待执行任务清单 | 🛑 等确认 |
| **3** | **逐任务循环**：标记 `[🔄]` → 预检三表 → Read 目标文件 → 精准实施 → 标记 `[x]` → 输出进度 | 命中 `forbidden.md` → **HARD BLOCK** |
| **4** | 更新 `progress.md` + 输出报告 + 写 eval-log | — |

**三张预检表**：`FORBIDDEN_LIST`（禁止项）、`TECH_ALLOWED`（已决策依赖）、`CODE_STYLE`（编码风格）。

**规范优先级（强制）**：`docs/rules/` > Design 规格 > Plan 描述 > 任何 Skill 建议。

**落盘数据**：`context_supplements`、`files_generated`（一次通过率的基数）、`interventions`。

---

## 阶段 6 · 代码审查 `/soda:cr`

**目标**：提交前把关，输出可被提交门禁消费的结论。

**输入**：当前分支 diff；模式参数 `--full` / `--key` / `--recheck`。

**执行步骤**

| Step | 做什么 |
|---|---|
| **0** | 加载 `code-reviewer` |
| **1** | 模式识别（fast 默认 / full / key / recheck），映射审查颗粒度 |
| **2** | 确定审查范围（`review-diff.sh` 行级精度；缺失则降级 `git log`）；空则终止 |
| **3** | 影响面分析（**fast 跳过**；key 必须执行），按 🔴/🟡/🟢 分级 |
| **4** | 向 code-reviewer 注入上下文（告知跳过其自身 Step 1/2） |
| **5** | 六维审查，每条标 `[BLOCKER]` / `[WARN]` / `[NIT]` |
| **6** | **BLOCKER 分支**：有 → 输出问题 → **终止，不落盘**；无 BLOCKER 有 WARN → 等确认 |
| **7** | 润色报告（fast 跳过） |
| **8** | 落盘 `.claude/cr-status.json`（含 `result` / `score` / `headCommit` / `issues[]`） |
| **9** | 输出结论 + 写 eval-log |

**score 公式**：`10 − BLOCKER×3 − WARN×1 − NIT×0.3`，最低 1 分。

**与提交门禁的闭环**：Step 6 终止时**不生成 `cr-status.json`**；而 `git commit` 的 PreToolUse 门禁要求该文件存在且 `result ≠ fail`——两道门禁互相咬合。

---

## 阶段 7 · 归档 `/soda:archive`

**目标**：收口需求，并把这次的资产变成下次可复用的知识。

**输入**：需求名（必填）+ ARD + Plan。

**执行步骤**

| Step | 做什么 |
|---|---|
| **1** | 前置检查（ARD + Plan 必须存在） |
| **2** | `git diff` 分类：`api_changed` / `db_changed` / `arch_changed` |
| **3** | 更新 `progress.md`，目录整体移动到 `completed/YYYY-MM/{需求}/` |
| **4** | **自动触发 `/soda:map --update`**；已有深档的域增量刷新；**`tech.yaml` 三向对账**（补登记 / 纠正版本 / 疑似已删待确认） |
| **5** | 提炼经验写入 `experiences/YYYY-MM-DD-{主题}.md`（无值得记的则跳过） |
| **6** | Humanizer 自检 |
| **6.5** | **归档自评**：`ai_dev_hours` 自动算；仅问 `manual_dev_hours` / `ai_code_ratio` / `notes` |
| **7** | 输出归档报告 |

**产物**：归档目录、经验文档、刷新后的知识图谱。

**注意**：`ai_dev_hours` **不询问、自动采集**（Σ 阶段时间戳）；`archive_assessment` 的键名是契约，写错会导致大盘整条丢弃。

---

## 阶段 8 · 评测 `/soda:eval`

**目标**：把 `eval-log.yaml` 变成人可读的报告和团队可聚合的数据。

**输入**：`eval-log.yaml`。

**执行步骤**

| Step | 做什么 |
|---|---|
| **1** | 解析项目名 / 分支名 / 需求名（`meta` 优先，git 兜底） |
| **1.5** | **Token 兜底补采**（上传前强制跑一次，幂等） |
| **2** | Read eval-log + HTML 模板 |
| **3** | inline Python 渲染单文件 HTML → `/tmp` |
| **4** | `upload_to_gift.py` → S3 PUT（对象路径 `{项目}/{分支}.html`） |
| **5** | `update_manifest.py` → GET / merge / PUT 团队大盘 |
| **6** | 输出两个 URL |

**红线**：报告里的一切过程数据**只能逐字取自 eval-log**，缺失就留空，禁止从其他来源推断补全。

**失败策略**：任一环节失败都不阻断，HTML 留在 `/tmp`。

## 跨阶段观察

### 1. 产出链是一条单向传送带

```
ARD ──→ Design ──→ Plan ──→ Test ──→ Impl ──→ CR ──→ Archive
 ↑影响域        ↑约束       ↑任务       ↑用例      ↑预检
```

每一阶段读上一阶段的产物；`docs/features/active/{需求}/` 就是这条传送带的物理载体。

### 2. 数据采集点分布

| 阶段 | 写入 eval-log 的特有数据 |
|---|---|
| `ard` | `context_checklist`（8 项） |
| `plan` | `unconfirmed_tasks` |
| `impl` | `context_supplements`、`files_generated` |
| `cr` | `bugs_found`、`bugs_p0`、`security_blocked` |
| `test` | `coverage_rate`、`defects_found`、`fix_attempts` |
| `archive` | `archive_assessment`（不走 eval-logger，由 archive 直接写） |

### 3. 一个真实的不一致：大纲确认只在 `ard` 有

`SKILL.md` 的 DOC 通道统一规定"输出文档大纲，等用户确认后再落盘"，但实际命令文件里：

| 命令 | 显式 `Step 3.5 输出大纲等确认` |
|---|---|
| `ard` | ✅ 有 |
| `design` | ❌ 无（润色后直接落盘） |
| `plan` | ❌ 无 |
| `test` | ❌ 无 |

**这意味着**：后三个阶段的"确认"依赖模型遵守 `SKILL.md` 的通用规则，而不是命令文件里的硬性停点。想更稳，可以把这四处对齐。

### 4. 另一个小缺口：`progress.md` 只看得到 5 个阶段

模板只有 ARD / Design / Plan / Test / Code 五行，**没有 CR 和 Archive**。CR 状态只在 `.claude/cr-status.json`，归档状态只能靠目录位置判断。

### 5. 停点的三种强度

| 强度 | 出现在 | 后果 |
|---|---|---|
| 硬阻断 / 硬终止 | 无 PRD、图缺失、`forbidden.md`、CR BLOCKER | 流程停下 |
| 停等确认 | Skills、大纲、任务清单、CR WARN | 等人回话 |
| 无停点 | design/plan/test 的落盘 | 直接写文件 |

---

## 一句话总结

> 八个阶段是**一条单向的文档传送带**：每个阶段消耗上一阶段的产物、产出一份新文档、写一段过程数据、并留下一个供下一阶段消费的约束；阶段之间必须人工推进，阶段内部靠 `HARD STOP` / `HARD BLOCK` 控制节奏。
