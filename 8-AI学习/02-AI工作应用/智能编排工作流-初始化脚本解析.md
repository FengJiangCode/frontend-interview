# 智能编排工作流 · 初始化脚本解析

> 解析对象：`scripts/init-project.sh`（约 680 行）
> 配套阅读：[智能编排工作流-速览卡.md](./智能编排工作流-速览卡.md)（15 分钟速览）、[AI落地项目-智能编排工作流.md](./AI落地项目-智能编排工作流.md)（完整版）、[智能编排工作流-门禁配置解析.md](./智能编排工作流-门禁配置解析.md)（门禁配置详解）、[智能编排工作流-运行时流程解析.md](./智能编排工作流-运行时流程解析.md)（运行时链路）

## 1. 它只做一件事

把 `.agents/skills/` 下的一个**静态分发包**，激活成一个**可运行的工作环境**。

激活产物 = **5 个部件 + 2 个配置点 + 3 个 git hooks**，全程遵守"技能层每次覆盖、项目层永不覆盖"的分野。

## 2. 逐步骤对照

| # | 脚本动作 | 落到磁盘 | 要点 |
|---|---|---|---|
| 0 | 检测项目类型 | `workflow.config.yaml: project.type` | 最关键的分叉，见 §3 |
| 1 | 建 docs 结构 | `docs/features/{active,completed}`、`docs/knowledge/`、`docs/rules/adr`、`docs/review` | 给流程准备"传送带"目录 |
| 2 | 生成 AI 规则 | `.claude/rules/rule.md`、`CLAUDE.md`、`docs/rules/*` | 见 §4.1 |
| 3 | 初始化门禁 | `.claude/settings.json` | 见 §4.2 |
| 4 | 生成项目配置 | `workflow.config.yaml` | 项目层，重跑不覆盖 |
| 5 | 更新 `.gitignore` | 追加技能层条目 | 技能层不进仓 |
| 6 | 生成 docs 说明 | `docs/README.md` | 文档空间自述 |
| 7 | 拉依赖 Skills | `.agents/skills/modules/` | 走内网 registry |
| 8 | 拉模板 | `templates/` | 同上 |
| 9 | 装 git hooks | `.git/hooks/{post-checkout,post-merge,post-rewrite}` | 配置变更自动重装 |
| 10 | 下发命令 + 注入 header | `.claude/commands/soda/*.md` | 见 §4.3 |

## 3. 最关键的分叉：`project.type`

脚本会自动检测项目类型，但也允许手动覆盖。这个字段是整套个性化配置的**总开关**——技能、模板、命令行为三者全部从它派生。

以两个类型的对比为例：

| | `frontend-h5` | `frontend-gattaran`（中后台 Vue） |
|---|---|---|
| 依赖技能数 | 13 个 | **15 个**（多 `field-config-designer`、`mid-backend-standards`） |
| 文档模板 | Fe 系列 3 个 | **Gattaran 系列 3 个** |
| `design` 加载技能 | 无 | `field-config-designer` |
| `impl` 加载技能 | `vue-standards-detector` | `mid-backend-standards` |

**结论**：`project.type` 一处改动，下游技能、模板、命令行为三者同步变化。这就是"类型感知"的实际含义。

## 4. 三处值得单独看的设计

### 4.1 `CLAUDE.md` 只写一行

```
@.claude/rules/rule.md
```

`RULE.md` 被**逐字节复制**到 `.claude/rules/rule.md`（可用 `diff` 验证完全一致），而 `CLAUDE.md` 只保留一个 `@` 引用。

这是"常驻成本控制"的落点：规则本身需要常驻上下文，但**入口文件保持极薄**。改规则只改一处，入口不动，也不会让每次新对话固定吞掉一大段上下文。

#### `rule.md` 的内容大纲

全文五章，分工非常清楚：

| 章节 | 内容 | 管什么 |
|---|---|---|
| **零、上下文加载策略** | Tier 1 规则层常驻 / Tier 2 知识层按意图路由 / Tier 3 源码按需读；附"每个命令读哪些知识节点"的映射表 | 读什么 |
| **一、触发模式** | 命令模式为唯一触发方式 + 13 条命令路由表 + 命令解析兜底规则 | 何时动 |
| **二、代码基座与风格规范** | ① 语言级规约跟随（Java→Alibaba、Python→PEP8、Go→gofmt、JS/TS→Google Style，**项目 Linter 配置优先**）② 规范化注释（JavaDoc/Godoc/JSDoc，不写"这个函数做了什么"式废话）③ 动笔前先想清楚（未核实不动笔，多种解读列出来让用户选）④ 最小代码原则（只写当前所需，200 行能写成 50 行就重写） | 怎么写 |
| **三、代码产出铁律** | ① **五维自检**：功能完备性→安全性→性能→可测试性→整洁度 ② 超 3 段中文文档过 `Humanizer-zh` ③ 多步任务先列计划 + 验证点，每步完成即验证 ④ 需求变更信号 → 先 `/soda:sync` 再动代码 | 交付前查什么 |
| **四、容灾边界约束** | ① 靶向替换红线（局部替换、遵循 OCP、清理本次孤儿、不擅自删已有死代码）② 边界调用必须有防线（异常全包裹 + 结构化日志 + 降级，**禁止吞错误**）③ 全局脏数据防火墙（非空校验、越界判断、可选链） | 哪里会出事 |

一句话概括这五章：**零章管"读什么"，一章管"何时动"，二章管"怎么写"，三章管"交付前查什么"，四章管"哪里会出事"。**

其中两处最值得单独记：

- **铁律 4（变更信号先同步文档）** 是"文档先行"的规则层表达——真正的硬拦截由 `before_impl_check.sh` 的时序检查兜底（ARD 比 Design 新 → 软警告）。
- **五维自检**是机械层查不了的部分：`after_code_scan.sh` 只能扫 `eval()`、密钥这类可正则化的红线，而"功能是否完备、是否可测试"必须由 AI 按这条规则自检后写进交付报告（`impl` 的 Step 4 会输出 `五维: X/5 通过`）。

### 4.2 门禁配置是"双层 × 三类挂点"

```
PostToolUse(Write|Edit)       → after_code_scan.sh     + haiku 查 ARD / Design 质量
PreToolUse(Bash git commit*)  → before_commit_check.sh + haiku 查 CR 状态
UserPromptSubmit              → before_impl_check.sh
```

每个挂点都是**机械层（shell）+ 语义层（haiku 小模型）**配对：

- 能用正则表达的（`eval()`、内网 IP、私钥、敏感信息）走 shell——快、零 token、可测试
- 判断不了语义的（"方案是否完整""CR 结论是否有效"）交给小模型读 `hooks/*.md` 规则

两个容易被忽略的细节：

- **`"disableAllHooks": true`** 先全局关闭 hook 自动发现，再逐条显式声明要装的。这是**白名单式**配置，避免未知 hook 被意外执行。
- 这一步**刻意排在拉取依赖之前**（脚本内注释写明：`fetch 前，不受网络影响`）。断网也能先把门禁装上。

#### 门禁配置的具体大纲

**① 文件结构（三层）**

```json
{
  "_doc": "注释字段，运行时忽略",
  "disableAllHooks": true,
  "hooks": {
    "UserPromptSubmit": [ { "hooks": [ … ] } ],
    "PreToolUse":       [ { "matcher": "Bash", "hooks": [ … ] } ],
    "PostToolUse":      [ { "matcher": "Write|Edit", "hooks": [ … ] } ]
  }
}
```

外层按**事件**分组，中层用 `matcher` 筛工具，内层可以挂**多个钩子并行执行**。

**② 四组挂点，共六条钩子定义**

| 挂点 | 触发条件 | 类型 | 检查内容 | 力度 |
|---|---|---|---|---|
| `UserPromptSubmit` | 无 matcher，每条消息 | `command` | 意图识别 → Design/Plan 存在性、ARD 与 Design 时序、Design 新鲜度、Git 状态、分支、构建配置 | 缺 Design/Plan **硬阻断**；其余软警告 |
| `PreToolUse` | `Bash` + `if: Bash(git commit*)` | `command` | CR 结果为 fail、暂存增量含敏感信息 / 内网 IP / 私钥、`console.log` / `debugger` / `vConsole` | 前三类**硬阻断**；后三类软警告 |
| 同上 | 同上 | `agent`（haiku） | 读 `hooks/before_commit.md`：hotfix 场景识别、CR 状态校验、headCommit 一致性 | 按规则输出结论 |
| `PostToolUse` | `Write\|Edit` | `command`（`async` + `asyncRewake`） | `eval()` / `new Function()` / 硬编码密钥 / `v-html` 绑变量 / `innerHTML` / `document.write`；`console.log` / `debugger` / 硬编码中文 / `TODO` / `http://` | 前六类**硬阻断**；后五类软警告 |
| 同上 | `Write` + `if: Write(**/ARD-*.md)` | `agent`（haiku） | 读 `hooks/after_ard.md`：需求覆盖度、边界完整性 | 输出结论 |
| 同上 | `Write` + `if: Write(**/Design-*.md)` | `agent`（haiku） | 读 `hooks/after_design.md`：架构完整性、技术栈一致性、接口完整度、高风险节点隔离 | 输出结论 |

**③ 一句话看懂分工**

```
机械层（shell）  → 能写成正则的：安全红线、敏感信息、调试残留
语义层（haiku）  → 判不了正则的：方案是否完整、CR 结论是否有效
```

同一个挂点下两层**并行执行**，并用 prompt 显式划分职责——`before_commit.md` 那段写着"跳过 Step 3 敏感信息扫描，已由 Shell 脚本独立执行，无需重复"，就是为避免两层重复劳动。

**④ 三级力度**

| 力度 | 谁决定 | 表现 |
|---|---|---|
| **硬阻断** | `exit 2` | 宿主拦截调用（或唤醒模型），输出回灌 |
| **软警告** | `exit 0` + 输出 | 提示但不拦 |
| **静默** | `exit 0` + 无输出 | 完全不留痕迹，保持上下文干净 |

> 字段级语义（`matcher` / `if` / `type` / `asyncRewake` / `timeout` 等）见 [智能编排工作流-门禁配置解析.md](./智能编排工作流-门禁配置解析.md)。

### 4.3 命令下发时会做"header 注入"

`commands/soda/*.md` 不是原样拷贝，而是**按 `workflow.config.yaml` 为每个命令生成一段"Skill 加载顺序"表头**，插到文件最前面。

注入结果示例（`frontend-gattaran`）：

| 命令 | 注入的 Skill 加载顺序 |
|---|---|
| `ard` | `brainstorming` → `Humanizer-zh`（固定） |
| `design` | `field-config-designer` → `Humanizer-zh` |
| `test` | `test-driven-development` → `Humanizer-zh` |
| `cr` | `code-reviewer` → `Humanizer-zh` |
| `fix` | `bug-analyse` → `Humanizer-zh` |
| `impl` | `mid-backend-standards` → `Humanizer-zh` |
| 其余命令 | 仅 `Humanizer-zh` |

**意义**：命令文件不再硬编码自己依赖哪些技能，依赖关系收敛到 config 一处。换项目类型时，命令内容自动跟着变。

## 5. 发现的问题

### 5.1 真实 bug：`impl.md` 的 header 被注入了两次

现象——`.claude/commands/soda/impl.md` 里存在两个 header：

```
1. mid-backend-standards   ← 本次配置，正确
2. vue-standards-detector  ← 陈旧残留，不该存在
```

根因——源头仓库的 `commands/soda/impl.md` **自带一个已提交的陈旧 header**（对比 `commands/soda/impl.md` 的三份副本：源头 1 个、其他命令 1 个且正确、唯有 impl 是 2 个）。而 init 的注入逻辑是"读源文件 → 前面插入新 header → 写目标"，**不清理已有 header**。

影响——执行 `/soda:impl` 时会先 Read `mid-backend-standards`，**再额外 Read 一遍 `vue-standards-detector`**，多加载一份不该用的规范。

建议——上游修两处：注入前先剥离已有 header；同时清掉源码里那个误提交的 header。

### 5.2 脚本自身的几处小毛病

| 问题 | 表现 |
|---|---|
| `show_result` 的条件判断写法 | `[ "$SKILL_DIR" == "$HOME/.claude"* ]` 在字符串含空格时报 `[: too many arguments`，导致"下一步"提示打印错乱 |
| 步骤编号不一致 | 前半是 `[0/9]`～`[5/9]`，到 `init_settings` 变成 `[3/10]`，两套编号混用 |
| `update_gitignore` 判重不严 | 用 `grep -q "^${entry}$"` 判断条目是否已存在；条目若被改成注释形式则匹配不到，重跑 init 会再追加一行，产生重复 |

## 6. 重跑的幂等性

升级工作流版本 = 重跑 init。各产物的行为分两类：

| 类型 | 产物 | 重跑行为 |
|---|---|---|
| **项目层** | `workflow.config.yaml`、`docs/rules/`、`docs/README.md` | 已存在则**跳过** |
| **技能层** | `.claude/commands/`、`.agents/skills/modules/`、`templates/`、`.claude/rules/rule.md` | 每次**全量覆盖** |

一个例外要注意：**`.claude/settings.json` 已存在时直接跳过**，除非显式加 `--force`。也就是说改了 `hooks-init.sh` 或想刷新门禁配置，必须手动 `--force`，否则改动不生效。

## 7. 一句话总结

> `init` 把研发流程从"一个技能包"变成"一套项目环境"：规则、命令、门禁、依赖、文档骨架五件套落位；其中**技能层每次覆盖以保证统一升级，项目层只在首次创建以保证项目个性化**；而全部个性化，由 `project.type` 一个字段派生。
