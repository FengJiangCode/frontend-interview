# 智能编排工作流 · 运行时流程解析

> 解析对象：一次需求的完整执行链路（从一条命令到落盘、度量、归档）
> 配套阅读：[速览卡](./智能编排工作流-速览卡.md)、[完整版](./AI落地项目-智能编排工作流.md)、[初始化脚本解析](./智能编排工作流-初始化脚本解析.md)、[门禁配置解析](./智能编排工作流-门禁配置解析.md)、[八阶段大纲](./智能编排工作流-八阶段大纲.md)、[数据采集与上报](./智能编排工作流-数据采集与上报.md)

## 0. 运行时的本质

不是"模型自主规划"，而是三件事的组合：

```
命令触发的剧本执行  +  宿主层门禁拦截  +  落盘文档构成的状态机
```

一句话：**AI 按剧本走，脚本在剧本之外拦，文档在磁盘上记。**

## 1. 一次命令触发的完整链路

```
用户输入 /soda:ard 某需求
        ↓
【宿主层】UserPromptSubmit hook 先跑（模型还没开始处理）
        └─ before_impl_check.sh：意图识别 → 非 impl 意图 50ms 内静默退出
        ↓
【规则层】RULE.md 命令解析兜底：收到 /soda:<name> 必须 Read
          .claude/commands/soda/<name>.md，按该文件执行
        ↓
【剧本层】读取命令文件 → 按 Step 顺序执行
        ├─ header：先按序 Read 配置声明的 input Skill
        ├─ 各 Step 内部：HARD STOP 等确认 / HARD BLOCK 终止
        └─ 末步：落盘 + 更新 progress.md + 写 eval-log
        ↓
【工具层】Write/Edit 后触发 PostToolUse hook
        └─ after_code_scan.sh：安全快扫（asyncRewake，出事才叫醒）
```

**关键认知**：存在**两层拦截时序**——hook 在模型处理之前，剧本在模型处理之中。两者不重叠，共同构成门禁。

## 2. 命令文件的执行模型

命令文件不是代码，是**一段自然语言剧本**。运行时它依赖四个机制：

| 机制 | 说明 |
|---|---|
| `$ARGUMENTS` | 用户输入替换占位符（如 `/soda:ard 某某需求`） |
| header | init 注入的"Skill 加载顺序"，决定执行前先 Read 哪些依赖技能 |
| Step 编号 | 顺序执行；`-1` / `-0.5` 表示前置步骤 |
| 显式停顿 | `🛑 HARD STOP`（等人）与 `🚫 HARD BLOCK`（终止） |

**没有解释器**——是模型读文档、按文档行动。所以"流程"的强度完全依赖：文档写得是否明确 + 门禁是否兜底。

## 3. 六个文档命令的固定骨架

| Step | 动作 | 约束 |
|---|---|---|
| **-1** | 确认项目类型 + 收输入 | `ard` 无 PRD → **HARD BLOCK** |
| **0** | 装上下文（知识图谱探针） | 图缺失 → **HARD STOP**，可回"跳过"降级 grep |
| **1** | 按序执行 input Skill | **每个 Skill 单独确认**（确认隔离原则） |
| **1.5 / -0.5** | 执行 inputSlot 跨阶段切片 | 自门控：上游无产出则跳过 |
| **2** | 读模板 | `config.output` > `project.type` 默认 > 嗅探 |
| **3** | 中文润色（Humanizer） | 固定动作 |
| **3.5** | 🛑 输出大纲等确认 | **确认前禁止写文件** |
| **4-5** | 落盘 + 更新 progress.md | 路径与文件名固定 |
| **末步** | 写 eval-log | "必须执行，不得跳过" |

> 各阶段的差异主要在 Step 0 和 Step 1：`ard` 的知识图谱探针最重，`design/plan` 侧重读上游文档，`test` 侧重测试矩阵。

## 4. 一次命令运行时读什么（上下文装配）

按加载层级由外到内：

| 顺序 | 内容 | 来源 |
|---|---|---|
| 1 | **常驻层**：项目铁律 + 知识路由器 | `CLAUDE.md` 的 `@` 引用，已在 context |
| 2 | **input Skill** | 命令 header 声明的顺序 |
| 3 | **知识图谱** | `ard` Step 0.0 强制探针：`index.md` → 域深档 / `navigation/*.json` |
| 4 | **inputSlot 切片** | 如 `great-ui-plus` 的 `<skill>/<stage>.md` |
| 5 | **模板** | `commands.<cmd>.output` |
| 6 | **上游产物** | 同目录的 ARD / Design / Plan |

**关键设计**：常驻层只放薄路由器，其余全部按需读——避免每次对话固定吞掉大量上下文。

## 5. 运行时的状态机：`docs/features/active/{需求名}/`

一个需求对应一个目录，目录里的文件构成传送带：

```
{需求名}/
├── ARD-{需求名}.md
├── Design-{需求名}.md
├── Plan-{需求名}.md
├── Test-{需求名}.md
├── progress.md          ← 五阶段状态机
└── eval-log.yaml        ← 过程数据
```

`progress.md` 的四态：

| 标记 | 含义 |
|---|---|
| ⏳ | 待开始 |
| 🔄 | 进行中 |
| ✅ | 已完成 |
| 🚫 | 阻塞 |

**阶段推进时自动改两行**：本阶段置 ✅，下一阶段置 🔄。

> 一个可注意的缺口：`progress.md` 模板只有 ARD / Design / Plan / Test / Code 五行，**没有 CR 和 Archive 行**。所以 CR 的状态只存在 `.claude/cr-status.json` 里，`progress.md` 看不到。

## 6. 拦截点全景

运行时一共有四类停：

| 类型 | 位置 | 表现 | 例子 |
|---|---|---|---|
| **宿主硬阻断** | hook `exit 2` | 工具调用被拦截 | 缺 Design/Plan 就写代码、暂存区有内网 IP |
| **剧本硬终止** | `HARD BLOCK` / 分支终止 | 本轮命令停止 | 无 PRD、命中 `forbidden.md`、CR 有 BLOCKER |
| **剧本停等** | `HARD STOP` | 停下来等人确认 | 输入 Skill 完成、文档大纲、待执行任务清单 |
| **软警告** | `exit 0` + 输出 | 提示但继续 | 工作区脏、在 main 分支、`console.log` |

**最能说明设计的是 CR 的 Step 6**：

```
有 BLOCKER → 输出问题列表 → 终止执行 → 不落盘、不进入后续 Step
```

也就是说，**CR 没通过时连 `cr-status.json` 都不会生成**，而提交门禁又要求该文件存在（或走 fix 分支）——两道门禁形成闭环。

## 7. 数据落盘时序

每个阶段结束时固定三件事：

```
① 文档落盘（ARD / Design / Plan / Test）
② 更新 progress.md（本阶段 ✅，下阶段 🔄）
③ 调用 eval-logger 写 eval-log.yaml
```

`archive` 阶段更重：

```
① 校验 ARD + Plan 存在
② git diff 分类（api / db / arch 变更）
③ 目录移动到 completed/YYYY-MM/
④ 自动触发 /soda:map --update（刷新知识图谱）
⑤ tech.yaml 三向对账（依赖清单 ↔ 快照）
⑥ 提炼经验写 experiences/
⑦ 人工自评 → 写 archive_assessment
```

`eval` 阶段：

```
① 解析项目/分支/需求名（meta 优先，git 兜底）
② token 兜底补采（强制跑一次）
③ 渲染单文件 HTML → /tmp
④ 上传 S3 → 更新大盘 manifest
```

## 8. 几个特殊运行路径

### 8.1 `impl` — 唯一按任务粒度循环的阶段

```
标记 [🔄] → 规范合规预检 → Read 目标文件 → 精准实施 → 标记 [x] → 输出进度
```

预检对照三张表：`FORBIDDEN_LIST`（命中即 HARD BLOCK）、`TECH_ALLOWED`（未列依赖需确认）、`CODE_STYLE`。

支持 `--from <任务编号>` 断点恢复；已标记 `[x]` 的任务自动跳过。

### 8.2 `cr` — 四种模式，路径不同

| 模式 | 影响面分析 | 审查范围 | 报告 |
|---|---|---|---|
| `fast`（默认） | 跳过 | 全量文件 | 只报 BLOCKER |
| `full` | 执行 | 全量文件 | 六维全审 |
| `key` | 必须执行 | 只审 🔴 高风险 | 其余标"已跳过" |
| `recheck` | 复用上次结果 | 只审上次 BLOCKER 文件 | 全量颗粒度 |

CR 结论落盘为 `.claude/cr-status.json`，含 `result`（pass / conditional_pass / fail）、`score`、`headCommit`、`issues[]`。

**score 公式**：`10 − BLOCKER×3 − WARN×1 − NIT×0.3`，最低 1 分。

### 8.3 `sync` — 补丁通道

需求变更时不重跑整条流水线，而是精准修代码 + 扫描受影响文档 + 只改相关段落，追加 `> 变更记录：[日期] [摘要]`。

**禁止大面积覆写**，用 `[~]` 标记废弃节点。

### 8.4 `map` — 三种扫描模式

| 模式 | 用途 |
|---|---|
| 全量 | 首次建图 / 大重构后 |
| `--update` | 按 `base_commit` diff，只刷受影响节点及 1-2 跳 |
| 单域深档 | 对某业务域生成 product / frontend 叙事文档 |

## 9. 线上时序（含 hook 介入点）

```
你：/soda:ard <需求>
  │
  ├─[hook] UserPromptSubmit → 意图识别（ard 不命中 impl，静默）
  │
  ├─ 读命令文件 → 读 input Skill
  ├─ Step -1 收 PRD（缺失 → HARD BLOCK）
  ├─ Step 0 知识图谱探针（输出带 file:line 的报告）
  ├─ Step 1 brainstorming（逐个确认）
  ├─ Step 3.5 🛑 输出大纲等你确认
  │       你：确认
  ├─ Step 4 落盘 ARD
  ├─ Step 5 progress.md：ARD ✅ / Design 🔄
  └─ Step 6 写 eval-log
        │
        └─[hook] PostToolUse → after_code_scan（扫描刚写入的文件）

你：/soda:design
  └─ …（同上，读 ARD + 影响域）

你：/soda:impl
  │
  ├─[hook] UserPromptSubmit → 命中 impl 意图
  │        └─ 缺 Design/Plan → exit 2 硬阻断（在模型开始前）
  │
  ├─ Step 0.5 加载 docs/rules/ 三份规约
  ├─ Step 2 输出任务清单等你确认
  └─ Step 3 逐任务循环
           │
           └─[hook] PostToolUse → after_code_scan
                    ├─ 有 eval() → exit 2 + asyncRewake 唤醒模型
                    └─ 无问题 → 静默

你：/soda:cr
  └─ Step 6 有 BLOCKER → 终止，不落盘

你：git commit
  └─[hook] PreToolUse → CR fail / 敏感信息 → exit 2
```

## 10. 异常与降级

| 异常 | 降级策略 |
|---|---|
| 知识图谱缺失 | 提示先建图；用户回"跳过"则降级 grep |
| 图谱落后 > 20 文件 | 提示刷新；可接受偏差继续 |
| input Skill 未安装 | 部分阶段降级（如 CR 降级为六维自检） |
| code-reviewer 缺失 | CR 降级为纯六维自检，报告标注"降级模式" |
| eval-log 写入失败 | 单行警告，不抛异常 |
| token 采集失败 | 静默跳过（`exit 0`） |
| S3 上传失败 | HTML 留在 `/tmp`，不落项目目录 |
| 文档模板缺失 | 视为软警告，报告标注 |

**总原则**：**数据采集和上报失败不阻断开发；安全和流程完整性失败必须阻断。**

## 11. 怎么判断它真的在跑（观测点）

| 观测点 | 看什么 |
|---|---|
| `statusMessage` | 终端转圈提示（📋 代码安全快扫…） |
| 落盘路径 | 命令结束会打印「已保存至 …」 |
| `progress.md` | 阶段状态是否推进 |
| `eval-log.yaml` | 是否有本阶段的时间戳和介入记录 |
| `.claude/cr-status.json` | CR 是否真的执行并落盘 |
| `docs/knowledge/manifest.yml` | `base_commit` 是否与当前 HEAD 对得上 |

## 12. 运行时的四条设计约束

| 约束 | 含义 | 原因 |
|---|---|---|
| **无自动流转** | 阶段之间必须手动敲下一条命令 | 可控、可审计、责任边界 |
| **确认隔离** | 说 OK 只推进一个 Skill | 防止批量跳过 |
| **文档先行** | 未落盘不得进入下一阶段 | 用物理门禁对抗跳步 |
| **单一触发** | 非命令消息不加载任何 Skill | 避免无谓消耗和误触发 |

> 这四条合起来，就是"AI 是执行者，人是签字人"这句话的运行期实现。

## 13. 一句话总结

> 运行时 = **命令触发的剧本 + 宿主层的门禁 + 磁盘上的状态机**。它不追求让 AI 一口气做完，而是把每一步都变成"可确认、可拦截、可追溯"的动作。
